# Step 5: Generate Langfuse setup

Produce a Langfuse setup document (`5. langfuse-setup.md`) with sections 5A–5K.

**Audience note:** this document is for a data scientist who may be new to Langfuse. Teach the vocabulary in the project's own terms before diving into structure.

**Mandatory-content rule.** Every section below is required unless a Step 1/2 verdict prunes it (e.g. no frontend → no human score flow); pruned sections must say **"N/A — [reason]"**, never be silently dropped.

## 5A. Core Langfuse concepts mapped to this project

Explain each concept below using THIS project's vocabulary (not generic examples). This is the section that prevents the most common confusion — capturing traces but not understanding how they link to results and feedback.

| Concept | Definition | What it maps to in this project |
|---------|-----------|--------------------------------|
| **Trace** | One complete job from start to finish, with a single `trace_id`. | One [primary task unit] (e.g., one video analysis request, one essay marking run). Name the unit explicitly. |
| **Span** | One step within a trace; has start/end, inputs, outputs; nests. | Each pipeline stage from Step 1. |
| **Generation** | A special span for an LLM call — adds model, prompt, completion, token counts, cost. | Each LLM call in the pipeline. |
| **Score** | A quality judgment attached to a trace/span/generation. Human, automated, or LLM-as-judge. | Human flags from the app + offline eval metrics + optional judge scores. |
| **Session** | A group of related traces. | A meaningful batch for this domain (e.g., all jobs from one source in one day/hour, one user upload batch). Define the grouping that lets you zoom from single traces to patterns. |

Emphasize the **trace_id is the glue** point: it must be generated by the backend, stored in the app DB alongside results, passed to the frontend for human scores, and used by the eval pipeline to write scores back.

## 5B. Trace structure

Map the pipeline stages (from Step 1) into nested spans. Present in two formats:

**Format 1: Compact tree** — a concise, scannable tree showing the trace hierarchy. Use this format in the HTML overview page as well (see html-overview reference for styling):

```
Trace: [primary_task_id] (one per [primary task unit])
├── Span: [stage_1]
│   ├── Span: [sub_stage] → Generation: [llm_call_name] (tokens, cost)
│   ├── Span: [sub_stage] → Generation: [llm_call_name]
│   └── ...
├── Span: [stage_2] (deterministic post-processing)
├── Span: [stage_3] (multi-mode only)
├── Span: [parallel_stage] → Generation: [embedding_call]
├── Span: [parallel_stage]
└── Span: [final_stage] → Generation: [llm_call_name]
```

**Format 2: Detailed breakdown** — for each span, specify: inputs captured, outputs captured, and metadata fields. For each LLM generation, specify: model, prompt template reference, token counts, latency. Include a complete worked example in section 5K.

## 5C. Metadata design

**Trace-level metadata** — things you'll filter/slice by:
- Scenario dimension (venue_type, document_type, etc.)
- Specific instance ID (venue_id, user_id, etc.)
- Template/prompt version
- Input characteristics (duration, length, complexity)
- Pipeline config (chunk size, model version, etc.)
- Environment (production vs eval run)

**Span-level metadata** — per-stage diagnostics:
- Output counts (people detected, matches found, events extracted)
- Confidence scores
- Processing time
- Error indicators

**Tags** — quick binary labels for filtering:
- User-flagged
- Low confidence
- Boundary event
- From eval run
- New scenario/source

## 5D. Score design

| Score name | Type | Source | Attached to | Purpose |
|------------|------|--------|-------------|---------|
| human_flag | numeric (0/1) | App user | Trace | Did user disagree? |
| human_flag_reason | categorical | App user | Trace | Error classification (see taxonomy rule below) |
| [primary_metric] | numeric | Eval pipeline | Trace | Offline eval result |
| [secondary_metric] | numeric | Eval pipeline | Trace | Offline eval result |
| [component_metric] | numeric | Component eval | Specific span | Stage-level quality |
| fairness_disparity_[axis] | numeric (0–1) | Fairness eval | Trace | Disparity ratio for demographic axis — **one score per axis listed in eval-plan 3G**, all axes covered, names matching |
| adversarial_pass | numeric (0/1) | Adversarial eval | Trace | Did system behave correctly on adversarial input? (only when adversarial track applies) |

**`human_flag_reason` taxonomy rule:** a categorical score is useless without its categories. The generated document must enumerate the reason values (derived from the system's failure modes, e.g. `not_an_incident`, `wrong_type`, `wrong_time`, `wrong_person`, `duplicate`) and state where the frontend surfaces them. If the app has no reason-capture UI yet, say so and specify the taxonomy as the requirement for that UI.

**Per-trace scores are point values.** CIs and noise bands live in the aggregate eval report (eval-plan 3H), not on individual trace scores. Do not attach intervals to per-trace scores.

## 5E. How scores flow in

```
Source 1: App users → flag incorrect results → score on trace
Source 2: Eval pipeline → golden dataset comparison → scores on traces
Source 3: Automated checks → proxy metric violations → tags on traces
Source 4: LLM-as-judge (optional) → narrative quality rating → score on generation
Source 5: Safety/fairness eval (when applicable) → adversarial_pass + fairness_disparity_[axis] → scores on traces
```

## 5F. Dashboards

**Dashboard 1: System health** (daily, automated alerts)
- Volume, latency, error rates, cost
- Alert when things break

**Dashboard 2: Model quality** (weekly review)
- Human flag rates and reasons, by scenario
- Trends over time
- Template comparison

**Dashboard 3: Eval results** (per eval run)
- Metrics vs baseline, per scenario
- Pass/fail gate visualization
- Regression highlights

**Dashboard 4: Component diagnostics** (on-demand, during error analysis)
- Per-stage metrics
- Proxy metric trends
- Boundary/merge statistics

## 5G. Alerts

| Alert type | Condition | Action |
|------------|-----------|--------|
| System down | Volume drops significantly | Investigate ingestion |
| Stage failure | Error rate spikes for a component | Notify engineers |
| Latency spike | p95 exceeds threshold | Check API/infra status |
| Quality drop | Human flag rate spikes for a scenario | Trigger targeted eval |
| Distribution shift | Proxy metrics drift beyond threshold | Run component eval |
| Cost anomaly | Daily cost exceeds budget | Check for retry loops, anomalous inputs |

## 5H. Integration points

Specify what each team needs to implement:

**Engineers must:**
- Import Langfuse SDK, wrap pipeline stages in spans
- Attach metadata to traces (from the metadata design)
- Store trace_id alongside results in the app's database
- Pass trace_id to frontend (for human score attachment)

**DS must:**
- Configure dashboards and alerts
- Build eval pipeline (golden dataset → run → write scores back)
- Define proxy metric thresholds
- Set up LLM-as-judge evaluators (optional)

## 5I. Common misconceptions to preempt

Include in the document (for the DS audience):
1. Langfuse is a sink — data flows IN, it doesn't pull from your databases
2. Trace ID is the glue — must be stored in app DB and passed to frontend
3. Not real-time — it's a record for analysis, not a live alert system
4. Sampling — start 100%, scale down once baselines established (never sample away user complaints)
5. Prompt management — optional but powerful for template versioning
6. Datasets feature — built-in offline eval tooling (alternative to custom pipeline)
7. Cost tracking — automatic if generations are instrumented correctly

## 5J. Implementation phases

| Phase | What | Dependency | Outcome |
|-------|------|-----------|---------|
| 1 | Instrument backend with SDK | Backend exists | Traces flow |
| 2 | System health dashboard + alerts | Traces flowing | Daily monitoring |
| 3 | Human score integration | App frontend exists | User feedback captured |
| 4 | Eval pipeline → scores | Golden dataset ready | Offline eval in Langfuse |
| 5 | Quality + diagnostic dashboards | After first eval run | Full picture |
| 6 | Prompt management (optional) | When template changes frequent | Auto-versioning |

## 5K. Full worked trace example

Include ONE concrete, fully populated trace for a realistic instance of the primary task — not a skeleton. Show a specific input flowing all the way through, with real-looking values at every span. This is what makes the abstract structure click for the reader.

For each span include: time window, inputs, outputs, and the span/generation metadata from 5C. For the LLM generation(s) include model, token counts, and template version. End the example with the scores block (human + eval scores) attached to the trace.

**Internal-consistency requirement (checked in Step 7):** every value in the example must reconcile with every other — event counts before/after each stage, merge/gap decisions against the stated thresholds, timestamp offsets, token totals across generations, and score values against the events shown. Scores in the example are per-trace point values — no CIs (see 5D).

```
Trace: tr_[id]
├── Metadata: {[scenario_dimension]: "...", template: "...", [instance_id]: "...", duration/length: ...}
│
├── Span: "[stage 1]" [t0 – t1]
│     Input: [concrete input]
│     Output: {[concrete output values]}
│     Metadata: {[stage-specific counts/timings]}
│
├── Span: "[stage 2]" [t1 – t2]
│     ├── Span: "[sub-stage]" → {[concrete values]}
│     └── Generation: "[LLM call]"
│           Model: [model]; Tokens: {input: N, output: M}
│           Metadata: {template_version: "...", ...}

│
├── Span: "[aggregation/merging]" [t2 – t3]
```

Populate every bracket with domain-specific, believable values drawn from Step 1.
