### Parallel GPU Pipelines (independent — raw video only, no Gemini output)

These take only the raw video as input. They do NOT use Gemini's analysis results. Triggered independently by user action (ROI: draw a box; Faces: click "Re-index").

```
Video ──▶ D-FINE GPU ──▶ Person detections (ROI line-crossing counts)
Video ──▶ InsightFace GPU ──▶ Face embeddings (512-d) ──▶ S3 Vectors (face index)
```

## Gemini Video Analysis — In/Out

### INPUT to Gemini (per chunk)

| Component | Content |
|-----------|---------|
| **Video Part** | `Part(file_data=FileData(file_uri=gcs_path, mime_type), video_metadata=VideoMetadata(fps=0.5, start_offset="30s", end_offset="60s"))` |
| **System Prompt** | Built from venue template: guardrail fragments + `{behavior_categories}` + `{venue_orientation}` |
| **User Prompt** | Task instructions + `{enabled_behavior_list}` (comma-separated keys) |

#### Gemini Request Config:
```python
GenerateContentConfig(
    temperature=analysis.temperature,        # 0.0–2.0
    seed=analysis.seed,
    media_resolution=gemini_resolution,      # LOW / MEDIUM / HIGH
    response_mime_type="application/json",
    response_schema=schema_class,            # Per-venue Pydantic model
    system_instruction=system_prompt,
    thinking_config=ThinkingConfig(thinking_level=analysis.thinking_level)
)
```

#### System Prompt Placeholders (from `prompt_builder.py`):
- `{occupancy_gate}` — min people before flagging
- `{authority_identification}` — teacher/staff recognition rules
- `{detection_threshold}` — severity floor
- `{evidence_requirement}` — what counts as evidence
- `{confidence_calibration}` — HIGH/MEDIUM/LOW criteria
- `{null_result_handling}` — what to do when nothing detected
- `{analysis_guidelines}` — general instructions
- `{person_identification}` — ID rules
- `{behavior_categories}` — numbered blocks: key, description, subcategories, do_not_flag
- `{venue_orientation}` — camera position + reference point + spatial guidance

#### Prompt Substitution Pipeline

`build_system_prompt()` assembles the final prompt in three passes:

```
1. Fragment substitution
   substitute_fragments(template_text, venue_label, authority_label, authority_indicators)
   └── Replaces all 8 guardrail placeholders with rendered text from fragments.py
       • occupancy_gate, authority_identification — parameterized (use venue_label / authority config)
       • detection_threshold, evidence_requirement, confidence_calibration,
         null_result_handling, analysis_guidelines, person_identification — static text blocks

2. Dynamic placeholder replacement
   .replace("{behavior_categories}", categories_text)   ← build_behavior_categories_text()
   .replace("{venue_orientation}", orientation_text)     ← build_orientation_text()
   .replace("{{duration_description}}", desc)           ← "2-minute clips" etc.

3. Tidy blank lines
   _tidy_blank_lines() — collapse 3+ consecutive newlines left by empty fragments
```

`build_user_prompt()` assembles the user message in the same three passes:

```
1. Fragment substitution (same as system prompt)
   substitute_fragments(template_text, venue_label, authority_label, authority_indicators)
   └── Same 8 guardrail placeholders available if referenced in the user prompt template
       (in practice, default user prompts don't use them — but custom templates can)

2. Dynamic placeholder replacement
   .replace("{enabled_behavior_list}", behavior_list)   ← comma-separated enabled keys
   .replace("{{duration_description}}", desc)           ← "2-minute clips" etc.
   Note: NOT {behavior_categories} or {venue_orientation} — those belong in the system prompt

3. Tidy blank lines
   _tidy_blank_lines() — same cleanup
```

#### System vs User Prompt Roles

| Role | Gemini field | Purpose | Content |
|------|-------------|---------|---------|
| **System** | `system_instruction` | "Who you are and all the rules" | Venue role statement, all 8 guardrail fragments, full behaviour category definitions (descriptions + subcategories + do_not_flag), spatial orientation, scoring rubric |
| **User** | Message content (alongside video) | "What to do with this specific clip" | Step-by-step task instructions (verify occupancy → identify authority → observe → detect), enabled category keys, duration description |

The video is attached as a `Part(file_data=...)` alongside the user prompt text.

#### Design Notes

1. **`{enabled_behavior_list}` is a compact echo of the system prompt's `{behavior_categories}`.**
   Both are built from the same filtered set (enabled behaviours only). The system prompt gets verbose numbered blocks (key + description + subcategories + do_not_flag). The user prompt gets just the comma-separated keys as a concise reminder inside the step-by-step instructions. Same set, different verbosity.

2. **Fragment substitution in `build_user_prompt()` is a safety net, not a default pattern.**
   The 8 guardrail placeholders are *available* in user prompt templates for flexibility (e.g. prompt engineering experiments that relocate a guardrail). But if a custom template references a fragment in both templates, Gemini receives the identical text block twice — once in `system_instruction`, once in `contents` — which is pure token waste with no behavioral benefit. The default templates are designed correctly: fragments only appear in `system_prompt_template`.

### OUTPUT from Gemini (structured JSON)

#### How Pydantic schemas control Gemini's output

The Pydantic class serves dual purpose — it constrains what Gemini produces AND validates the response:

```
Pydantic class (e.g. ClassroomAnalysisResult)
    │
    ├── Before call: converted to JSON Schema → sent as response_schema in config
    │                (Gemini is forced to produce output matching this shape)
    │
    └── After call:  model_validate_json(response.text) → typed Python object
                     (validates + deserializes the raw JSON string)
```

```python
# In analysis_service.py:
schema_class = get_schema_for_venue("classroom")  # → ClassroomAnalysisResult

config = GenerateContentConfig(
    response_mime_type="application/json",
    response_schema=schema_class,          # Pydantic → JSON Schema → Gemini constraint
    system_instruction=system_prompt,
    ...
)

response = client.models.generate_content(
    model="gemini-3-flash-preview",
    contents=[video_part, user_prompt],
    config=config,
)

result = schema_class.model_validate_json(response.text)  # Parse raw JSON into typed object
```

#### Pydantic Schema Definitions (`models/schemas.py`)

```python
class RiskLevel(str, Enum):
    HIGH = "HIGH"
    MEDIUM = "MEDIUM"
    LOW = "LOW"
    NONE = "NONE"


class Incident(BaseModel):
    behavior_type: str              # Free-form, matches venue template behavior keys
    behavior_subcategory: str | None
    timestamp_start_seconds: float | None   # Relative to chunk start (offset added during merge)
    timestamp_end_seconds: float | None
    description: str                # Detailed narrative of actions observed
    confidence: RiskLevel           # HIGH | MEDIUM | LOW | NONE


class ClassroomAnalysisResult(BaseModel):
    any_inappropriate_behavior_detected: bool
    fighting_detected: bool
    fighting_summary: str | None
    bullying_detected: bool
    bullying_summary: str | None
    subtle_bullying_detected: bool
    subtle_bullying_summary: str | None
    item_throwing_detected: bool
    item_throwing_summary: str | None
    phone_usage_detected: bool
    phone_usage_summary: str | None
    eating_detected: bool
    eating_summary: str | None
    laptop_misuse_detected: bool
    laptop_misuse_summary: str | None
    classroom_disruption_detected: bool
    classroom_disruption_summary: str | None
    incidents: list[Incident]
    student_reaction: str | None
    scene_description: str
```

#### Per-Venue Result Schemas:

| Venue | Schema | Behaviour-specific `*_detected` / `*_summary` pairs |
|-------|--------|---------------------|
| Classroom | `ClassroomAnalysisResult` | fighting, bullying, subtle_bullying, item_throwing, phone_usage, eating, laptop_misuse, classroom_disruption |
| Exam Hall | `ExamHallAnalysisResult` | cheating, phone_usage, unauthorized_communication, unauthorized_materials, looking_at_others_papers |
| Canteen | `CanteenAnalysisResult` | overcrowding, food_waste, queue_cutting, fighting, littering |
| Library | `LibraryAnalysisResult` | noise, sleeping, unauthorized_food, phone_usage |
| Corridor | `CorridorAnalysisResult` | running, loitering, fighting, bullying, vandalism |
| Custom | `GenericAnalysisResult` | None — incidents list only |

All schemas share these universal fields:
- `any_inappropriate_behavior_detected: bool`
- `incidents: list[Incident]`
- `scene_description: str`

Venue-specific schemas add `*_detected` / `*_summary` pairs per behaviour category. `GenericAnalysisResult` has no pairs — custom venues use only the `incidents` list with free-form `behavior_type` strings.

## Gemini vs GPU Sidecars — Hosting Distinction

| | Gemini | GPU Sidecars (D-FINE, InsightFace) |
|---|---|---|
| **Who runs the model** | Google (managed API) | Our team (own container, own GPU instance) |
| **Where** | Google's Vertex AI infrastructure | Cloud Run service with attached L4 GPU |
| **Cost model** | Per-token API pricing | Per-second GPU instance billing |
| **Why** | Proprietary multimodal model, no alternative | Open-source models with no hosted API; cheaper at scale to self-host |
| **End-user GPU?** | No — server-side | No — server-side |

All inference is server-side in GCP. The end user's device is never involved.

## D-FINE GPU Sidecar — In/Out (Person Detection)

| | |
|---|---|
| **In** | `DetectRequest { gcs_input_uri, roi: {x1,y1,x2,y2}, fps_sample, expansion_factor, score_threshold }` |
| **Out** | `DetectResponse { detections: [{t_seconds, bbox, confidence, intersection_over_roi, track_id}], frames_sampled, video_duration_seconds, expanded_roi }` |

Used for ROI zone-presence analytics (detecting people entering/dwelling in a user-drawn region).

### Backend Orchestration Layer (roi_analysis_service + event_aggregator)

The D-FINE sidecar is **stateless** — it returns raw per-frame detections and nothing else. All business logic lives in the main backend:

```
User draws ROI on video → POST /videos/{id}/roi-analyses
       │
       ▼
┌──────────────────────────────────────────────────────────────────┐
│  1. ROI Analysis Service (backend only — no sidecar call)        │
│     • Writes Firestore doc (status=pending)                      │
│     • Queues Cloud Task → /internal/pipeline/roi-process/{id}    │
└──────┬───────────────────────────────────────────────────────────┘
       │ Cloud Task fires
       ▼
┌──────────────────────────────────────────────────────────────────┐
│  2. D-FINE Sidecar Call (with retry: 3 attempts, exp backoff)    │
│     ┌────────────────────────────────────────────────────────┐   │
│     │  SIDECAR (GPU)                                         │   │
│     │  • Downloads video from GCS                            │   │
│     │  • Samples frames at fps_sample (default 2 fps)        │   │
│     │  • D-FINE object detection → person bboxes per frame   │   │
│     │  • ROI expansion + overlap test (bbox ∩ expanded ROI)  │   │
│     │  • ByteTrack identity linking across frames            │   │
│     │  • Writes progress to Firestore every 5s (live bar)    │   │
│     │  Returns: per-frame detections                         │   │
│     │    [{t_seconds, bbox, confidence,                      │   │
│     │      intersection_over_roi, track_id}]                 │   │
│     └────────────────────────────────────────────────────────┘   │
└──────┬───────────────────────────────────────────────────────────┘
       │
       ▼
┌──────────────────────────────────────────────────────────────────┐
│  3. Event Aggregation (backend, no sidecar call)                 │
│     • Groups consecutive detections into presence events          │
│     • Gap tolerance: 10s (frames >10s apart = new event)         │
│     • Min duration: 5s (drops sub-5s blips / false positives)    │
│     • Per event: start_t, end_t, max_concurrent_people,          │
│       peak_confidence, unique_track_count, track_dwell_breakdown │
└──────┬───────────────────────────────────────────────────────────┘
       │
       ▼
┌──────────────────────────────────────────────────────────────────┐
│  4. Summary Stats (backend, no sidecar call)                     │
│     • total_events                                               │
│     • total_dwell_seconds                                        │
│     • peak_concurrent_people                                     │
│     • longest_event_seconds                                      │
│     • events_per_hour                                            │
│     • unique_track_count (upper bound — re-entry = new track)    │
└──────┬───────────────────────────────────────────────────────────┘
       │
       ▼
┌──────────────────────────────────────────────────────────────────┐
│  5. Persist to Firestore + GCS (backend, no sidecar call)        │
│     • events + summary → Firestore roi_analyses doc              │
│     • Raw detections → GCS JSON blob (Firestore 1MB doc limit)   │
│       with presigned URL for frontend bbox overlay toggle        │
└──────────────────────────────────────────────────────────────────┘
```

**Only step 2 touches the GPU sidecar.** Steps 1, 3–5 are pure backend logic (CPU, no ML inference). This means:
- Aggregation parameters (gap tolerance, min duration) can be re-tuned without re-running the GPU — just re-aggregate the stored detections
- The sidecar handles detection + tracking; the backend handles temporal interpretation

**Key design note:** D-FINE is a standard object detector (bboxes + confidence per frame). ByteTrack (multi-object tracking, Kalman filter) runs **inside** the sidecar to link same-person bboxes across frames via spatial proximity — this is what produces `track_id`. But the temporal grouping into "dwell events" (what's meaningful to the user) happens in the backend.

**What the frontend shows:**
- Timeline with colored event segments (seekable — click to jump to that point)
- Summary card: total events, peak people, dwell time, events/hour
- Per-event expandable cards with duration, confidence, track breakdown
- Optional bbox overlay on video player (fetches raw detections from GCS)

## InsightFace GPU Sidecar — In/Out (Face Embedding)

The sidecar exposes two endpoints, both stateless:

| Endpoint | Purpose | When it runs |
|----------|---------|--------------|
| `/detect_embed_video` | Bulk indexing — sweep a video chunk for all faces | Auto (on analysis complete, if gallery exists) or manual ("Re-index" button) |
| `/embed_image` | One-shot probe — embed a specific face the user pointed at | User-triggered only (never automatic) |

### `/detect_embed_video` — Bulk Face Indexing (write path)

| | |
|---|---|
| **In** | `DetectEmbedVideoRequest { gcs_input_uri, start_seconds, end_seconds, fps_sample=0.5, det_score, min_face_size_px, include_thumbs }` |
| **Out** | `DetectEmbedVideoResponse { faces: [{bbox, landmarks[10], det_score, embedding[512], quality: {size_px, blur, yaw_estimate}, aligned_thumb_b64, scene_thumb_b64, frame_t}] }` |

Embeddings: **512-dim ArcFace** (L2-normalized). `frame_t` is the absolute timestamp in the source video.

### `/embed_image` — Interactive Face Probe (read path)

| | |
|---|---|
| **In** | `EmbedImageRequest { gcs_input_uri, bbox, det_score, min_face_size_px, include_thumbs }` |
| **Out** | `EmbedImageResponse { faces: [{bbox, landmarks[10], det_score, embedding[512], quality, aligned_thumb_b64}], image_width, image_height }` |

No `frame_t` (it's a still image). The optional `bbox` filter scopes detection to a specific face the user clicked. Used for the "find this person" kNN query and roster enrollment — see **Appendix: Face Probe Search Flow** below.

### Backend Orchestration Layer — Face Indexing (face_indexing_service.py)

The InsightFace sidecar is **stateless** — it returns face detections with embeddings and thumbnail crops. All identity matching, deduplication, storage, and aggregation lives in the main backend. The orchestration calls **`/detect_embed_video`** (the bulk endpoint) once per chunk window:

```
Trigger: Gemini analysis completes (auto, if user has gallery)
         OR user clicks "Re-index faces" (manual)
       │
       ▼
┌──────────────────────────────────────────────────────────────────┐
│  1. Build chunk windows (backend only — no sidecar call)         │
│     • Union [start_s, end_s] from all completed analyses         │
│     • Deduped so overlapping analyses don't re-process same time │
└──────┬───────────────────────────────────────────────────────────┘
       │ parallel (3 concurrent max — matches sidecar max-instances)
       ▼
┌──────────────────────────────────────────────────────────────────┐
│  2. Per-window: call InsightFace sidecar /detect_embed_video     │
│     ┌────────────────────────────────────────────────────────┐   │
│     │  SIDECAR (GPU)                                         │   │
│     │  • Downloads video from GCS                            │   │
│     │  • Samples frames at fps_sample (default 0.5 fps)      │   │
│     │  • SCRFD face detection → per-face bboxes              │   │
│     │  • ArcFace embedding (512-d, L2-normalized)            │   │
│     │  • Quality assessment (blur, yaw, size)                │   │
│     │  • Aligned 112×112 crop + 256×256 scene crop           │   │
│     │  Returns: list of VideoFaceHit (bbox, embedding,       │   │
│     │           landmarks, det_score, quality, thumbs, frame_t) │
│     └────────────────────────────────────────────────────────┘   │
└──────┬───────────────────────────────────────────────────────────┘
       │
       ▼
┌──────────────────────────────────────────────────────────────────┐
│  3. Intra-chunk deduplication (backend, no sidecar call)         │
│     • Same person in consecutive frames → near-identical embeds  │
│     • Collapse by cosine threshold (keep highest det_score crop) │
│     • Prevents flooding the index with N copies of a static face │
└──────┬───────────────────────────────────────────────────────────┘
       │
       ▼
┌──────────────────────────────────────────────────────────────────┐
│  4. Gallery matching (backend, no sidecar call)                  │
│     • Load user's enrolled student gallery once (all embeddings) │
│     • For each face: exhaustive cosine dot product vs gallery    │
│     • ≥ 0.70 → "confident" (auto-stamped, no review needed)     │
│     • 0.55–0.70 → "candidate" (shown as "likely X" in UI)       │
│     • < 0.55 → unknown (no student_id stamped)                  │
└──────┬───────────────────────────────────────────────────────────┘
       │
       ▼
┌──────────────────────────────────────────────────────────────────┐
│  5. Thumb upload (backend → GCS, 8 parallel workers)             │
│     • Aligned 112×112 crop → GCS faces/{video_id}/{vector_id}   │
│     • Scene 256×256 crop + scene_bbox → same prefix (_scene)     │
│     • Returns GCS URIs to store on the vector metadata           │
└──────┬───────────────────────────────────────────────────────────┘
       │
       ▼
┌──────────────────────────────────────────────────────────────────┐
│  6. Bulk-upsert to S3 Vectors (backend → AWS, batches of 100)   │
│     vector_id: "{video_id}:f{frame_t_centiseconds}_{face_idx}"  │
│     metadata: user_id, video_id, folder_id, student_id,         │
│               confidence_tier, det_score, frame_t, bbox,         │
│               aligned_thumb_gcs, scene_thumb_gcs, scene_bbox,    │
│               human_decision                                     │
└──────────────────────────────────────────────────────────────────┘
```

**Only step 2 touches the GPU sidecar.** Steps 1, 3–6 are pure backend logic (CPU, no ML inference). This means:
- Gallery matching logic can change without redeploying the GPU container
- Deduplication thresholds can be tuned without re-running detection
- The sidecar is reusable — it just produces embeddings; the backend decides what to do with them

**Read-time aggregation (what the user sees):**

```
┌──────────────────────────────────────────────────────────────────┐
│  Per-student sighting summary                                    │
│  • "Alice — 12 sightings, best score 0.89, first seen 02:30"    │
│  • Ranked by count × score                                       │
├──────────────────────────────────────────────────────────────────┤
│  Unknown face clustering (greedy single-link by cosine)          │
│  • Groups unidentified faces by visual similarity                │
│  • Each cluster: representative thumb + count + sample grid      │
│  • Prevents N identical thumbnails for one unidentified person   │
├──────────────────────────────────────────────────────────────────┤
│  Per-clip top matches (top-3 students per chunk)                 │
│  • Ranked: confident-first, then by sighting count, then score   │
│  • Representative scene crop + bbox overlay for each             │
└──────────────────────────────────────────────────────────────────┘
```

**Additional backend operations (no GPU sidecar involved):**

| Operation | Trigger | What it does |
|-----------|---------|--------------|
| **Stamp refresh** | Student enrolled/unenrolled | Re-runs cosine match on all existing vectors for the user. Updates student_id stamps without re-running face detection. |
| **Operator decision** | Confirm/reject/clear button in UI | Sets `human_decision` on vectors within a clip. Confirmed stamps survive gallery changes; rejected stamps are excluded from counts. |
| **Sightings query** | Click a student's face tile | Sweeps all vectors by key prefix, filters by student_id, returns chronological list across all videos. |

**Key design note:** The InsightFace sidecar is a pure detection+embedding engine. All the "who is this person?" logic (gallery matching, confidence tiers, operator review, clustering) is backend application code that can evolve without touching the GPU container.

## How the Three Pipelines Relate (Frontend Integration)

The three AI components — Gemini, D-FINE, InsightFace — are **completely independent pipelines**. Sidecar output never feeds into Gemini, and Gemini output never feeds into the sidecars. The frontend renders them as separate panels on the same video page:

```
┌─────────────────────────────────────────────────────────┐
│ Video Detail Page                                       │
│                                                         │
│ ┌──────────────────┐  ┌──────────────────────────────┐ │
│ │ Gemini Analysis  │  │ Faces Panel (InsightFace)    │ │
│ │                  │  │                              │ │
│ │ - Incident       │  │ - Confident matches (≥70%)   │ │
│ │   timeline       │  │ - Candidate matches (55-70%) │ │
│ │ - Event list     │  │ - Unknown clusters           │ │
│ │ - Behavior flags │  │ - Confirm/reject buttons     │ │
│ └──────────────────┘  └──────────────────────────────┘ │
│                                                         │
│ ┌──────────────────────────────────────────────────────┐│
│ │ ROI Panel (D-FINE)                                   ││
│ │                                                      ││
│ │ - User draws a zone on the video                     ││
│ │ - Presence events timeline (who entered/left)        ││
│ │ - Dwell time, peak occupancy, per-track breakdown    ││
│ │ - Optional: per-frame bbox overlay on video player   ││
│ └──────────────────────────────────────────────────────┘│
└─────────────────────────────────────────────────────────┘
```

### Each pipeline is triggered independently

| Feature | User Action | What Runs | What's Shown |
|---|---|---|---|
| Behaviour analysis | Click "Analyze" | Gemini pipeline | Incident timeline + event cards |
| Person detection | Draw a box on video | D-FINE sidecar | Crossing events, occupancy counts, track IDs |
| Face identification | Click "Re-index" | InsightFace sidecar | Face tiles grouped by identity |

### Why they don't chain

| Capability | Gemini | D-FINE | InsightFace |
|---|---|---|---|
| Understand actions/intent ("is this stealing?") | Yes | No | No |
| Precise bounding boxes per frame | No | Yes | Yes |
| Frame-by-frame tracking with persistent IDs | No | Yes (ByteTrack) | No |
| Exact count of people crossing a line | No | Yes (ROI intersection math) | No |
| Identify same person across videos | No | No | Yes (512-dim cosine) |

Gemini handles **qualitative** analysis ("what behaviours are happening?"). The sidecars handle **quantitative** spatial tracking and **identity** matching — tasks that need deterministic numerical output at frame-level resolution. Gemini's video API has temporal slicing (start/end offset) but no spatial ROI parameter, so it cannot replace D-FINE's pixel-precise zone monitoring.

### The only merge point: Activity Dashboard

A cross-video **Activity feed** (`GET /api/v1/activity`) lists all running/completed jobs (both `kind: 'ai'` and `kind: 'roi'`) in one chronological stream. But they are listed together, not combined analytically — the user mentally correlates them.

Chaining them (e.g. D-FINE detects person in ROI at time T → narrow Gemini's focus to that timestamp for action recognition) is architecturally possible but **not wired up today**.

## Pipeline Modes

| Mode | Behaviour |
|------|-----------|
| **chunked** | Single chunk duration (default 30s). Steps: start → process-batch → merge |
| **multi_duration** | Multiple chunk durations (e.g. 30s, 60s, 300s, 600s) analyzed in parallel. Steps: start → process-batch → merge (per duration) → combine |
| **whole** | Legacy, now converted to chunked internally |

### Key Transformations During Merge

- **Timestamp offset**: `incident.timestamp_start_seconds += chunk_start_seconds`
- **Incident stitching**: consecutive same-type incidents within 5s gap → merged (highest confidence kept)
- **Event IDs**: `{analysis_id}_evt_{offset + i:04d}` (multi-duration offsets by `duration_index * 10000`)
- **Scene descriptions**: joined as `"[30s-60s] Classroom...\n[60s-90s] Quiz time..."`

## Appendix: User-Facing Search Flow

### Semantic Clip Search (user interaction → AI → results)

```
User types: "students fighting near the back"
         │
         ▼
┌─────────────────────────────────────────────────────────────────┐
│  Query Rewrite (optional, Gemini 3 Flash)                       │
│                                                                 │
│  IN:  raw query text                                            │
│  OUT: expanded description (15–30 words)                        │
│       e.g. "students fighting near the back" →                  │
│       "Physical altercation, pushing, punching between students │
│        in the back rows of a classroom or corridor"             │
│                                                                 │
│  • LRU-cached per instance (repeat queries skip Gemini call)    │
│  • Falls back to raw query on error — search never breaks       │
│  • Can be disabled per-request (expand_query=False)             │
└────────┬────────────────────────────────────────────────────────┘
         │
         ▼
┌─────────────────────────────────────────────────────────────────┐
│  Query Embedding (gemini-embedding-2, text-only)                │
│                                                                 │
│  IN:  expanded query text (or raw if rewrite disabled/failed)   │
│  OUT: 1536-d vector                                             │
│                                                                 │
│  Note: query embedding is TEXT-ONLY — unlike chunk indexing     │
│  which sends video + caption. Both land in the same 1536-d      │
│  space because gemini-embedding-2 is multimodal.                │
└────────┬────────────────────────────────────────────────────────┘
         │
         ▼
┌─────────────────────────────────────────────────────────────────┐
│  S3 Vectors kNN Query                                           │
│                                                                 │
│  Index: videoclips (1536-d, cosine distance)                    │
│  Score: 1 - cosine_distance (higher = more similar)             │
│  topK: over-fetches 3× requested, capped at 100 (S3 limit)     │
│                                                                 │
│  Metadata filters (AND):                                        │
│  • Tenant access: user_id OR shared folder_ids                  │
│  • Optional: folder_id, video_id, has_incidents, date range     │
└────────┬────────────────────────────────────────────────────────┘
         │
         ▼
┌─────────────────────────────────────────────────────────────────┐
│  Post-processing (in SearchService)                             │
│                                                                 │
│  • Per-video cap (default max 3 clips per video)                │
│  • Overflow count → "+N more in this video" UI affordance       │
│  • Enrich with presigned thumbnail URLs from GCS                │
│  • Return: [{video_id, chunk_idx, start_s, end_s, caption,      │
│             score, incident_categories, thumbnail_url, ...}]    │
└─────────────────────────────────────────────────────────────────┘
```

### Why query is text-only but index is multimodal

| | Indexing (per chunk) | Search (per query) |
|---|---|---|
| **Input to embedding model** | Video segment + caption text | Expanded query text only |
| **Why** | Caption biases the vector toward what was *detected* — "fighting" in the caption pulls the embedding toward fight-related queries | Users type text; there's no video to embed at query time |
| **Same vector space?** | Yes — gemini-embedding-2 maps both modalities into 1536-d | Yes — text query lands near multimodal chunks with similar semantics |

## Appendix: Face Probe Search Flow

### "Find this person" (user interaction → InsightFace sidecar → kNN)

This is the **read path** for face search — entirely user-triggered, never automatic.

```
User clicks a face on the video player
         │
         ▼
┌─────────────────────────────────────────────────────────────────┐
│  1. Frame Snapshot (backend, no GPU)                             │
│                                                                  │
│  • Backend seeks to the clicked timestamp, extracts one frame    │
│  • Uploads frame to GCS as a temporary .jpg                      │
│  • Records the bbox of where the user clicked                    │
└────────┬────────────────────────────────────────────────────────┘
         │
         ▼
┌─────────────────────────────────────────────────────────────────┐
│  2. InsightFace Sidecar: /embed_image                           │
│                                                                  │
│  IN:  gcs_input_uri (the snapshot .jpg) + bbox (clicked region) │
│  OUT: FaceHit { embedding[512], bbox, det_score, quality,       │
│                 aligned_thumb_b64 }                              │
│                                                                  │
│  • bbox filter: only returns faces whose center is inside the   │
│    clicked box — scopes to exactly the face the user selected   │
│  • Single image, no frame sampling (unlike /detect_embed_video) │
│  • No frame_t (it's a still image, not video)                   │
└────────┬────────────────────────────────────────────────────────┘
         │
         ▼
┌─────────────────────────────────────────────────────────────────┐
│  3. kNN Query against S3 Vectors faces index (backend, no GPU)  │
│                                                                  │
│  • Query vector: the 512-d embedding from step 2                │
│  • Distance: cosine (= dot product, since L2-normalized)        │
│  • Filters: user_id (tenant isolation), optional folder/video   │
│  • topK: up to 100 nearest face vectors                         │
│                                                                  │
│  Returns: face vectors that look like the clicked person,       │
│           ranked by cosine similarity                            │
└────────┬────────────────────────────────────────────────────────┘
         │
         ▼
┌─────────────────────────────────────────────────────────────────┐
│  4. Enrich results (backend, no GPU)                            │
│                                                                  │
│  • Group by video_id                                            │
│  • Attach video title, thumbnail URL                            │
│  • Return: "This person also appears in Classroom 3B at 2:30,   │
│    Library at 14:15, Corridor at 14:18..."                      │
└─────────────────────────────────────────────────────────────────┘
```

### Roster Enrollment (second flow using `/embed_image`)

```
Admin uploads class photo → backend uploads to GCS
         │
         ▼
┌─────────────────────────────────────────────────────────────────┐
│  InsightFace Sidecar: /embed_image (no bbox filter)             │
│                                                                  │
│  • Detects ALL faces in the class photo                         │
│  • Returns each face's embedding + aligned crop                 │
└────────┬────────────────────────────────────────────────────────┘
         │
         ▼
┌─────────────────────────────────────────────────────────────────┐
│  Backend: match faces to students                               │
│                                                                  │
│  • Admin assigns each detected face to a student name           │
│  • Backend stores embedding in Student.embeddings[]             │
│  • This becomes the "gallery" used for auto-matching in the     │
│    bulk indexing pipeline (step 4 in orchestration above)        │
│  • Triggers stamp refresh on all existing face vectors          │
└─────────────────────────────────────────────────────────────────┘
```

### Why `/embed_image` is separate from `/detect_embed_video`

| | `/detect_embed_video` (bulk) | `/embed_image` (probe) |
|---|---|---|
| **Purpose** | Populate the face index (write path) | Query the face index (read path) |
| **Input** | Video + time range | Single still image |
| **Sampling** | Multiple frames at fps_sample rate | One image, all faces at once |
| **Has `frame_t`?** | Yes (needed for timeline placement) | No (still image) |
| **Has `bbox` filter?** | No (detect everything) | Yes (scope to clicked face) |
| **Runs automatically?** | Yes (on analysis complete) | Never — always user-triggered |
| **Downstream** | → bulk upsert to S3 Vectors | → kNN query against S3 Vectors |
