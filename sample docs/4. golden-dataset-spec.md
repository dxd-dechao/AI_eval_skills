## 4B. Dataset Composition

### System goal classification

SmartCampus is a **safety-critical detection** system. The primary concern is missing real incidents (P0 false negatives), with a strong secondary concern about wrongful accusation (P1 false positives). This maps to:

- Heavy negatives (55%) — mirrors production reality where most video is uneventful
- Moderate positives (25%) — sufficient for per-cell CIs on P0/P1 behaviours
- Moderate edge cases (20%) — adversarial near-misses and ambiguous situations

**Deviation from default (60%+ negatives):** 55% negatives instead of 60%+ because the 6 venue types × 19 behaviour types create many cells that each need sufficient positives. At 55% negatives with 750 total items, each positive behaviour × venue cell averages 8–12 items — sufficient for per-cell point estimates but reliant on venue-level aggregation for CIs. Phase 2 growth targets n ≥ 100 per P0 behaviour × venue cell.

## 4D. Edge Cases

### Per-behaviour edge cases

| Behaviour | Looks like target but isn't | Why it's hard | What distinguishes it |
|-----------|---------------------------|---------------|----------------------|
| Fighting | Play-fighting, PE wrestling, drama rehearsal, high-five gone wrong | Similar physical contact patterns | Intent (facial expressions, aftermath), context (PE kit, teacher supervising) |
| Bullying | Friendly roughhousing, close friends being physical, birthday surprise | Repeated targeting vs one-off, power imbalance | Victim reaction (distress vs laughter), repeated pattern |
| Subtle_bullying | Animated conversation, friend group naturally excluding someone | Social dynamics vs sustained targeting | Duration, victim's body language (withdrawal, looking for help) |
| Cheating | Student stretching/looking up, adjusting glasses, reading own notes | Eye movement toward another paper vs general gaze | Sustained gaze direction, visible paper, furtive behaviour |
| Phone_usage | Calculator (allowed), checking time on wrist, adjusting hearing aid | Device in hand doesn't always mean phone | Duration, screen visibility, context (exam vs free period) |
| Running (corridor) | Late student rushing to class, PE transition, fire drill | Speed alone doesn't indicate misbehaviour | Context (bell time, group vs individual), carrying equipment |
| Overcrowding | Dense but orderly queue, event gathering | Density ≠ unsafe crowding | Movement patterns, distress, exit access, pushing |
| Loitering | Student waiting for friend, reading notice board | Static presence ≠ truancy | Duration, time of day (should they be in class?), behaviour |

## 4F. Matching Logic

A system output event **matches** a ground-truth event when:

1. **Same behaviour_type** (exact string match)
2. **Temporal overlap** within tolerance:
   - IoU(system_interval, gt_interval) ≥ **0.30**
   - OR system start time within **10 seconds** of ground-truth start time

**Tolerance justification (user utility):** A reviewer navigating to the system's reported timestamp should find the relevant content within a few seconds of scrubbing. At IoU ≥ 0.30, a 7-second ground-truth event matched by a 20-second system window still gives the reviewer a clear segment to review. The 10-second start-time fallback handles cases where the system reports a much wider window but the start is close enough to be useful.

**Implementation alignment:** The codebase's `_merge_consecutive_incidents` uses a 5-second gap tolerance for merging — our 10-second matching tolerance is 2× the merge gap, which means two separately-merged system events could both match a single ground-truth event spanning the gap. In such cases, credit the first match and mark the second as duplicate (not a false positive).

**Matching priority:** When multiple system events could match a single ground-truth event, assign the match to the system event with highest IoU. Unmatched system events are false positives; unmatched ground-truth events are false negatives.

## 4G. Metrics

| Metric | What it answers | Reporting format |
|--------|-----------------|-----------------|
| Detection recall | Of real events in the dataset, how many did the system find? | point [lower, upper] 95% CI (Wilson) |
| Detection precision | Of system outputs, how many correspond to real events? | point [lower, upper] 95% CI (Wilson) |
| Classification accuracy | Of detected events, how many have the correct behaviour_type? | point [lower, upper] 95% CI (Wilson) |
| Temporal IoU | How precisely do system timestamps overlap ground truth? | mean [lower, upper] 95% CI (bootstrap) |
| False positive rate on negatives | On clean videos, how often does the system hallucinate? | point [lower, upper] 95% CI (Wilson) |
| Edge case discrimination | On look-alike inputs, does the system correctly refrain from flagging? | point [lower, upper] 95% CI (Wilson) |
| Consistency | Across N=3 runs on same items, what fraction produce identical detection sets? | agreement_rate ± std |

All metrics reported per venue_type. When fairness track applies, additionally stratified by each demographic/condition axis with disparity ratios (bootstrap CIs).

## 4H. Acceptance Criteria for Dataset Items

| Criterion | Requirement |
|-----------|-------------|
| Minimum duration | ≥ 15 seconds per clip (sufficient context for behaviour detection) |
| Resolution | ≥ 720p (system processes at configurable media_resolution) |
| Camera angle | Must match one of the supported camera positions (back_wall, front_wall, ceiling_*, side) |
| Format | MP4 or MKV with H.264 video codec (system's supported formats) |
| Ground truth clarity | Behaviour must be unambiguously visible to a trained human reviewer |
| Production fidelity | Lighting, angle, and quality must be representative of real school CCTV |
| Privacy | All faces pixelated in storage; consent on file for any identifiable person |
| Temporal annotation | Timestamps accurate to ±1 second (verified by second annotator on edge cases) |

**Adjudication procedure:**
1. Edge-case and adversarial items are **double-labeled** by independent annotators
2. Report inter-annotator agreement (Cohen's κ for behaviour_type, IoU for timestamps) on the dataset version. The number is a quality report. It is not a keep-or-drop cutoff, and this spec does not set one.
3. Any disagreement goes to a named adjudicator. If the adjudicator cannot resolve it, exclude the item. Ambiguous ground truth stays out of both the development set and any later held-out set.
4. Record the adjudicator id, the agreement figure, and the include/exclude decision on the item. Do not treat a printed κ value as approval of the labels.
5. A random 10% of single-labeled positives/negatives are also double-labeled as an annotation quality check.

**Negative-item exception (4L Strategy 1):** clean negatives may enter the benchmark without per-item human review when auto-confirmed by the dual-model procedure in 4L. For those items the "ground truth clarity" criterion is enforced at the pipeline level — via the always-human-scrubbed drift-check sample — rather than per item.

## 4K. Annotation Process & Tooling

How the ground truth in 4E actually gets created: three tools for three kinds of GT, plus the chunk-alignment and pre-labeling rules.

### Where annotation happens

| Ground truth | Tool | Why |
|---|---|---|
| Event timelines (Layer 2 golden set; source for Stage 1/2 component GT) | **SmartCampus's built-in annotation projects** (`/api/v1/.../projects`, `routers/annotations.py`) | Already supports per-video timeline events with exactly the 4E fields (behavior_type, subcategory, start/end seconds, description, annotator confidence), per-annotator records for double-labeling, benchmark comparison, and JSON/CSV export. Annotators see the same player and timebase the system reports in. |
| Frame-level boxes: D-FINE person bboxes (200 frames), InsightFace face bboxes + identity labels (150 frames) | **External CV annotation tool** (CVAT or Label Studio) | The in-app tool has no bounding-box support. Export COCO-format → GCS, with in-repo manifests (harness Group C fixtures). |
| Named human reviews of system outputs, and any later held-out labels for an optional LLM route | **Langfuse annotation queues** | Humans record Pass/Fail on system outputs against one approved criterion version. Those labels are not the development set. |

> **Langfuse does NOT support video annotation.** Its annotation queues attach scores to traces/observations — no timeline scrubbing, no bounding boxes, no event drawing. Langfuse is where humans *score outputs* (named reviews, flag review). Ground truth is *created* in the two tools above and only its derived scores ever reach Langfuse.

### Timebase rule — annotate whole videos, derive chunks

- **Layer 2 labels: annotate the whole video in ABSOLUTE timestamps.** Never annotate per chunk: chunk duration is a config knob under evaluation (multi-duration runs 30/60/300/600s over the same video), so labels tied to one chunking would be invalid for every other config. Matching (4F) and any later criterion operate in absolute time.
- **Stage 1 chunk dataset (eval-plan 3C, 300+ chunks): derived mechanically, never re-annotated.** Slice the whole-video GT using the *same chunking arithmetic the pipeline uses* (call the pipeline's own chunk-boundary code), convert timestamps to chunk-relative, and clip events at boundaries. Events straddling a boundary are flagged `boundary_event` — these get a human verification pass; everything else transfers automatically. One source of truth, no double annotation, and Stage 2's boundary-scenario fixtures fall out of the same slicing.
- Stage 4 (summary triage) GT is event-list-level — no timebase concern.

### AI-assisted pre-labeling — allowed, with guardrails

The in-app tool can batch-approve/reject the system's own AI events into annotations (`source: manual | ai_approved | ai_rejected`, per `AnnotationSource` in `services/api/models/annotation_models.py`). This speeds up Phase 2 but risks anchoring GT to the system under eval (misses stay missed; timestamps inherit system boundaries). Guardrails:

1. **Full-scrub rule:** approving AI events never replaces watching the clip — every video gets a full timeline scrub for events the system missed. *Sole exception:* clean negatives auto-confirmed under 4L Strategy 1, where dual-model confirmation plus the drift-check sample substitutes for the per-item scrub (the carve-out and its validation are defined there).
2. **Blind items via label-first projects:** edge-case, adversarial, and the 10% drift-check sample (4H) are annotated in projects created **without `analysis_ids`** ("label-first" — supported today in `annotation_service.py`; with no linked analysis, `list_ai_events()` returns nothing and the AI track renders empty). **Blind is a property of the project, not the annotation:** on an analysis-linked project even hand-drawn annotations are anchored, because the annotator sees the AI track while drawing. DS maintains the label-first project list; analyses may be attached to such a project only after its annotation is complete (for benchmark comparison).
3. Approved AI-event timestamps are re-verified to the ±1s standard (4H), not accepted as-is.
4. **No bulk accept in golden projects:** the events list's "Accept pending with confidence ≥ HIGH/MEDIUM" bulk action skips per-event viewing and timestamp re-verification. It is a production-triage convenience — prohibited in golden-dataset annotation projects; every AI event is reviewed individually (`a`/`r` after watching).
5. The `source` field is preserved per annotation; the Phase 2 kappa report includes the ai-approved fraction and compares recall on blind vs AI-assisted items — any gap is measured pre-label bias. Rejected AI events (`ai_rejected`) are retained — they are confirmed false positives and feed the edge-case candidate pool (4L Strategy 7).
6. **Completion criterion:** a golden video is done when the **full timeline scrub** is complete AND every AI alert is individually reviewed. The in-app "X / Y AI alerts reviewed" progress bar tracks only the latter — it must not define done.

### Who draws what (D-FINE / InsightFace / ROI)

| Artifact | Who | Where |
|---|---|---|
| Person bounding boxes (Stage 5 GT) | Trained annotators | CVAT/Label Studio, frames sampled from golden videos stratified by venue × conditions |
| Face boxes + identity labels / verification pairs (Stage 6 GT) | Trained annotators; identity labels require consent, stored in the restricted partition | CVAT/Label Studio |
| Skin-tone & other fairness axes | Designated DS reviewers only (4J privacy rules) | Restricted partition (`golden_dataset_fairness/`) |
| **ROI lines/zones** | **Not annotation — product configuration.** In production, school admins draw ROIs in the app. For eval, **DS fixes a frozen set of ROI configs** on the golden videos, versioned with the dataset. | App ROI editor; config exported with the dataset version |
| Line-crossing counts (given the frozen ROIs) | Trained annotators count crossings by watching | In-app or spreadsheet against the frozen ROI overlay |

D-FINE's mAP/recall GT (person boxes) is independent of any ROI; ROI only matters for the crossing-count eval, which is why the ROI set must be frozen and versioned — changing the ROI silently invalidates crossing GT.

### Export → golden dataset

A conversion script (DS-owned) maps annotation-project exports to the 4E schema and the harness item schema (`eval_harness/dataset_loader.py`): annotations → `expected_output.events` with stable `gt_event_id`s; project/video records → item `metadata`, including **`blind_project: true|false`** derived from the DS-maintained label-first project list; `dataset_version` = content hash over the converted items. Frame boxes export as COCO → GCS + manifests. Re-running the script on unchanged annotations must be byte-identical (hash-stable).

## 4L. Annotation Burden Offloading

The annotation budget is the primary bottleneck in Phase 1–2. This section defines
approved automation strategies that reduce human effort **without compromising
benchmark integrity**. The core constraint remains: anything entering the primary
benchmark as a positive or edge case must have human-verified ground truth. The
offloading targets the high-volume, low-judgment work so humans spend their limited
time on the hard stuff (P0 timestamps, edge-case adjudication, adversarial crafting).

### Effort landscape

| Segment | Items | Human effort per item | Automation potential |
|---|---|---|---|
| Negatives | 310 | Low individually but high in aggregate (full scrub to confirm "nothing") | **High — auto-confirm candidates** |
| Positives (P0/P1) | 135 | Very high (precise timestamps, severity, double-label) | Low — must be human |
| Edge cases | 150 | High (double-labeled, adjudicated) | Low for *labeling* (blind by design) — **Medium for sourcing** (Strategy 7 confidence-stratified mining) |
| Adversarial (malformed subset) | 25 | Near-zero — programmatic perturbation | **Already automated** |
| D-FINE / InsightFace frames | 350 | Medium (bounding-box drawing) | **Medium — model-assisted pre-label** |
| ROI configs | ~50 videos | Low per-item but manual in app UI | **Medium — auto-detect + approve** |
| Stage 2/3 fixtures | unlimited | Zero | Already synthetic JSON |

### Strategy 1: Auto-confirmed negatives

**Problem:** 310 full-scrub annotations for "nothing happened" clips.

**Method:**
1. Run the production pipeline + a second independent model from a **different
   model family** (a non-Gemini VLM, e.g. a Claude or GPT-class video model, with
   a high-sensitivity prompt) on candidate negative clips.
2. If **both** models agree "no events" → auto-label as negative. Mark
   `annotation_metadata.source: "dual_model_confirmed"`. Operationalized as:
   zero incidents returned AND the scene_description is consistent with normal
   activity (models emit no confidence value for *absence* — the description
   check is the substitute).
3. Human reviews only the **disagreement set** (typically 10–15% of candidates).
4. The 10% random drift-check sample (4H) is always human-scrubbed regardless of
   model agreement — this validates the auto-confirm pipeline itself.

**Expected reduction:** ~260 of 310 negative items auto-confirmed → human effort
drops from 310 full scrubs to ~50 targeted reviews + 31 drift-check scrubs.

**Guardrails:**
- **The confirmer must be a genuinely different model family — never Gemini.** The
  production pipeline is Gemini (3 Flash). A Gemini confirmer would correlate the
  labeler with the system under eval, and with any later optional LLM route that
  also used Gemini. A real event both copies miss would enter as a clean negative,
  and a better future system that detects it would be scored as a false positive.
  That corrupts negative-item labels. Whether those labels feed a gate is a
  Product decision that this candidate spec has not approved.
- If no capable non-Gemini VLM is available, do not run this strategy at family
  parity — instead raise the human coverage (e.g. a 2×-speed skim of every
  auto-confirm candidate) and record the residual correlated-miss risk in the
  Phase 2 kappa report.
- This strategy is an explicit, documented exception to 4K's full-scrub rule and
  4H's per-item ground-truth-clarity criterion (both cross-reference it).
- Any clip with >3 people and moderate+ crowd density always gets human review
  (crowd dynamics are where negatives are hardest).
- The dual-model agreement rate is tracked; if it drops below 80% for a venue type,
  fall back to full human annotation for that venue.

### Strategy 2: Video augmentation for stress-test overlay

**Problem:** 190 positive clips are expensive to source and annotate; more coverage
is needed for per-cell CIs.

**Method:** Generate 2–3 augmented variants of each annotated positive clip using
deterministic video transforms that **do not alter the events**:

| Transform | Parameters | Annotation impact |
|---|---|---|
| Lighting shift | Brightness ±30%, contrast ±20%, colour temperature shift | None — events unchanged |
| Resolution downsample | 1080p → 720p → 480p | None |
| Mild spatial crop | Random 10–20% edge crop (simulating different FoV) | Timestamps unchanged; events at crop edge flagged for human verification |
| Temporal stretch | ±10% speed (0.9×–1.1×) | Timestamps scale proportionally — automated |
| Noise injection | Gaussian noise σ=5–15, compression artefacts (re-encode at CRF 35+) | None |
| Frame drop | Random 5% frame drop (simulating network glitch) | None |

**Implementation:** An `ffmpeg`-based augmentation script (`eval_harness/scripts/augment_golden.py`)
takes annotated items, applies transforms, and produces new items with transformed
metadata (duration adjusted for stretch, resolution updated). The `dataset_version`
hash covers augmented items separately — they form a **stress-test overlay dataset**
(`golden-v1-augmented`), never mixed into the primary benchmark.

**Expected yield:** 190 positives × 3 variants = 570 additional items with zero
new human annotation. Used for:
- Robustness evaluation (does performance degrade under visual perturbation?)
- Increasing effective sample size for per-cell CIs on the stress-test overlay
- Early development iteration (before real negatives are collected)

**Constraints:**
- Augmented items are **never** counted toward the primary benchmark's 750-item
  composition or its gate metrics.
- Spatial crops that remove >50% of persons involved in an event are discarded.
- The augmentation script is deterministic (seeded) and hash-stable.
- **CIs over the overlay must bootstrap by parent clip, not by item.** The 2–3
  variants of one parent are correlated samples; item-level bootstrap would be
  overconfident and violate 3H's independence assumptions.

### Strategy 3: Auto-ROI generation

**Problem:** DS must manually draw ROI lines/zones on ~50 golden videos for the
crossing-count eval. Drawing in the app UI takes 2–5 minutes per video.

**Method:**
1. For each golden video, extract a representative frame (median frame, or the
   frame with highest person count from a quick D-FINE pass).
2. Run a VLM (Gemini Flash) with the prompt: "Identify all entry/exit points
   (doors, corridor junctions, stairwells). For each, output a line segment in
   pixel coordinates that a person would cross to enter/exit."
3. Overlay the proposed ROI lines on the frame and present to DS for
   **approve/adjust** (binary review, not drawing from scratch).
4. For **negative videos**, crossing counts may be auto-derived by running a
   **pinned D-FINE version** + the ROI crossing logic — but these are a
   **regression baseline, not accuracy GT**. Counting normal traffic is exactly
   the task under evaluation ("no abnormal activity" does not mean no crossings),
   so an auto-derived count can only detect drift between D-FINE/config versions
   (analogous to Stage 7's pinned corpus). Absolute crossing-count accuracy is
   measured only against the human-counted sample (4K).

**Expected reduction:**
- ROI drawing: from 2–5 min/video (manual) to 15–30 sec/video (review + approve).
- Negative crossing counts: auto-derived regression baselines for the ~50
  crossing-eval videos (the crossing eval covers the frozen-ROI subset, not all
  310 negatives); human counting is reserved for a stratified accuracy sample.

**Guardrails:**
- VLM-proposed ROIs that don't align with any visible architectural feature (door,
  corridor, gate) are flagged for manual drawing.
- The frozen ROI config is still versioned and human-approved (this speeds up the
  approval, not replaces it).
- **Scope note:** the crossing-count eval is a Stage 5 extension, defined in
  eval-plan 3C Stage 5 as the "Line-crossing count error" metric — accuracy is
  measured only against the human-counted sample; auto-derived counts are
  regression baselines and never feed that metric or any gate.

### Strategy 4: Model-assisted bounding-box pre-labeling (D-FINE / InsightFace)

**Problem:** 200 D-FINE frames (person boxes) + 150 InsightFace frames (face boxes
+ identity) require manual bbox drawing.

**Method:**
1. Run a strong detector that is **not the model under evaluation** as pre-labeling:
   - D-FINE GT frames: pre-label with GroundingDINO (or another detector, or a
     prior D-FINE checkpoint that will never be an eval target) → candidate
     person boxes. Never pre-label with the D-FINE version being evaluated.
   - InsightFace GT frames: pre-label with a different face detector (e.g. MTCNN
     or YOLO-face) → candidate face boxes + preliminary identity clusters. Same
     rule: not the InsightFace detector under evaluation.
2. Import pre-labels into CVAT/Label Studio as editable annotations.
3. Annotators **correct** (add missed boxes, remove false detections, adjust
   boundaries) rather than drawing from scratch.

**Expected reduction:** Bbox annotation is typically 3–5× faster with pre-labels
than from scratch. ~200 frames × 4 min each (manual) → ~200 frames × 1 min each
(correction mode). Saves ~10 hours of annotation time.

**Guardrails:**
- **Pre-labels must never come from the model/checkpoint under evaluation** —
  circular GT would blind the eval to exactly the misses being measured.
- **Blind-from-scratch subset:** 10–15% of frames are annotated with pre-labels
  hidden. The missed-box rate on blind vs pre-labeled frames measures annotator
  complacency (automation bias) — the failure mode where annotators stop hunting
  for boxes the pre-labeler didn't propose. Mirrors Strategy 1's drift check.
- Quality gate: for any frame where the annotator changes >30% of pre-labeled boxes,
  flag for senior review (pre-label may be unreliable for that scene type).
- The `annotation_metadata` records `prelabel_model` and `correction_fraction` per
  frame for bias analysis.

### Strategy 5: Synthetic fixture generation (Layer 1 Groups A/B/D)

**Problem:** Component evals need large fixture sets for statistical power, but
hand-crafting JSON fixtures is tedious and limited in coverage.

**Method — per stage:**

| Stage | Generation approach | Free GT? |
|---|---|---|
| Stage 2 (merge) | Parametric generator: vary gap sizes (1s–30s), behaviour types, chunk counts, boundary overlaps, severity levels | Yes — expected merge output is deterministically computed from the input parameters |
| Stage 3 (combine) | Parametric generator: multi-duration result sets with known expected combined output | Yes — same logic |
| Stage 5 (D-FINE stress) | Composite frames: cut out person silhouettes from real frames, paste onto real venue backgrounds at varied positions/scales/occlusion levels | Yes — bbox GT = paste coordinates |
| Stage 7 (retrieval) | LLM paraphrase: take 100 golden queries, generate 3–5 semantically equivalent rephrasings each | Inherit relevance labels from parent query |

**Implementation:** Generator scripts live in `eval_harness/scripts/`:
- `generate_merge_fixtures.py` — produces `eval_harness/fixtures/merge/*.json`
- `generate_combine_fixtures.py` — produces `eval_harness/fixtures/combine/*.json`
- `generate_dfine_composites.py` — produces composite frames + COCO GT
- `generate_query_paraphrases.py` — produces paraphrased query items

**Expected yield:**
- Stages 2/3: 500+ parametric fixtures (from current ~30–50 hand-crafted) → much
  better boundary-condition coverage
- Stage 5: 500+ composite frames beyond the 200 real annotated frames
- Stage 7: 300–500 query variants from 100 golden queries

**Constraints:**
- Composite/synthetic items are labeled `source: "synthetic"` and tracked separately
  in metrics (never blended with real-data metrics without explicit notation).
- Paraphrased queries inherit the parent's relevance grades; any paraphrase that
  subtly changes meaning (verified by a second LLM check) is discarded.
- Parametric fixtures must cover known edge cases (zero-event chunks, max-event
  chunks, exact-boundary events, single-frame events) — the generator has explicit
  edge-case templates, not just random sampling.

### Strategy 6: Semi-automated Stage 4 triage labels

**Problem:** 50 event lists need ground-truth triage labels (which events are P0,
which are actionable, what's the summary). Writing triage from scratch is slow.

**Method:**
1. Run the production triage path on each event list to produce candidate triage
   output.
2. Present annotators with the candidate + a binary task: "Is this triage
   correct? If not, what's wrong?" The verification checklist **must explicitly
   ask "is any P0 event sitting in the noise group?"** per item — Stage 4's gate
   is P0-recall-in-review = 1.00, and a rubber-stamped candidate that wrongly
   deprioritized a P0 event would bake that exact failure into the GT.
3. A 10-item blind subset — **5 randomly sampled + 5 hardest multi-event
   scenarios** — is annotated with no candidate shown, as calibration anchors.
   The random half estimates anchoring bias on typical items; the hard half
   stresses the ceiling. (Hardest-only would be a selection confound.)

**Expected reduction:** Binary verification is ~5× faster than writing triage from
scratch. Baseline 50 items × 10 min = 500 min; with offloading, 40 items × 2 min
(verify) + 10 items × 10 min (blind) = 180 min remaining → **~320 min (~64%)
saved**.

### Strategy 7: Confidence-stratified edge-case mining + the feedback loop

**Problem:** the edge-case segment's real cost is not labeling 150 clips — it is
*finding* 150 genuinely hard ones (4C sources them from production FPs and staged
look-alikes). Meanwhile, annotator verdicts on low-confidence detections are
valuable feedback that should improve the system — without contaminating the
benchmark.

**Method — selection by confidence stratum (uncertainty sampling):**

| Stratum | Why it's boundary material | Action |
|---|---|---|
| LOW/MEDIUM-confidence AI detections | The model itself is unsure — near its decision boundary | Sample into the edge-case candidate pool → blind-label (label-first project, 4K) |
| `ai_rejected` annotations | Confirmed production false positives — "the most valuable edge cases" (4C) | Harvest directly into the look-alike sub-segment candidate pool |
| HIGH-confidence detections later flagged wrong by users | Confident *and* wrong — the most informative failures | Priority candidates |
| HIGH-confidence, human-confirmed detections | Far from the decision boundary | Skip — low edge-case value |

The same stratification orders human review queues in the other strategies
(Strategy 1's disagreement set, Strategy 4's flagged frames): most-informative
items first.

**Guardrails:**

- **Selection ≠ labels.** Confidence chooses *what* enters the labeling queue;
  it never touches *how* items are labeled. Mined clips are blind-labeled via
  label-first projects (4K), and 4H double-labeling is never sampled down.
- **Provenance:** each mined item records `selected_by: {stratum, model_version}`.
  A confidence-selected segment is adversarial relative to the *selecting*
  model's boundary — good for regression testing ("did we fix what we knew was
  hard"), but edge-case scores are **not comparable across model generations**
  as if difficulty were fixed.
- **Model-independent core:** the staged look-alike portion (4D taxonomy —
  human-designed) stays free of model-based selection, so the segment never
  becomes a pure mirror of the current model's boundary. Refresh the mined
  portion each model generation.

**The feedback loop — what labels can and cannot tune:**

Gemini 3 Flash is a frozen API model: there is no gradient path from annotations
into its weights ("the model tunes its own confidence" is not possible).
Feedback flows at three levels instead:

| Level | Mechanism | Status |
|---|---|---|
| 1. Template/prompt adaptation | Labels → error analysis → venue-template edits (behaviour descriptions, `do_not_flag` entries, text exemplars of confused cases). Already gated: every template edit re-runs Stage 1 + Layer 2 (eval-plan 3E) | Native to the architecture — use now |
| 2. Confidence calibration table | Observed precision per behaviour × venue × emitted-confidence cell → deterministic remap of displayed confidence / triage order. Requires ≥ 50 labels per cell (3H small-cell rule); refreshed monthly; versioned; if adopted, it is a new deterministic component and gets its own component eval (calibration error before/after) | Future — when label volume supports it |
| 3. CV sidecar tuning | D-FINE score threshold (0.35) or fine-tuning on annotated boxes; InsightFace match thresholds (0.70/0.55) on verification pairs. Local, open-weight models — true label→retrain active learning is possible here | As needed — gated by Stage 5/6 evals |

Gemini fine-tuning is ruled out even where Vertex supports it: every tuned
variant is a new model version that voids noise bands and forces full
re-baselining (3E) — template edits deliver the adaptation without that cost.

**Contamination rule (hard precondition):** an item whose label influenced the
system in any way (template edit, calibration cell, threshold change) can never
sit in the golden gate set — that is train/test contamination. Golden items are
frozen and never train anything. The feedback pool is: production
`verification_status` flags, `ai_rejected` harvests, and annotation projects
outside `golden-v*`. Movement is **one-way**: feedback pool → golden set (with
fresh blind labels only), never the reverse direction of influence.

| Strategy | Items affected | Effort reduction | Risk level |
|---|---|---|---|
| 1. Auto-confirmed negatives | 310 | ~80% less human scrub time | Medium (correlated-miss risk; mitigated by cross-family confirmer + drift check) |
| 2. Video augmentation | 190 → 760 | Zero new annotation for 570 items | Very low (deterministic transforms; parent-clip bootstrap for CIs) |
| 3. Auto-ROI | ~50 videos | ~80% faster per video | Low (human approves ROIs; auto counts are regression-only, never accuracy GT) |
| 4. Model-assisted bboxes | 350 frames | ~70% faster per frame | Low (never pre-label with model under eval; blind subset measures automation bias) |
| 5. Synthetic fixtures | Stages 2/3/5/7 | 10× more coverage, near-zero human cost | Very low (deterministic GT) |

### Phase 0 integration

These strategies integrate into the Phase 0 timeline (4I):
- Augmentation script and fixture generators are built during Phase 0 (Jul 2026).
- **The contamination split (golden vs feedback pool, Strategy 7) is established
  in Phase 0** — before any labels exist to leak.
- Dual-model negative confirmation pipeline is validated during Phase 1 collection.
- Model-assisted pre-labeling is configured in CVAT/Label Studio before Phase 2
  annotation begins.
- Auto-ROI generation runs once when golden videos are finalized (early Phase 2).

  flags accumulate — from Phase 2 onward, feeding edge-case growth and the
  Phase 4 quarterly dataset expansion.
