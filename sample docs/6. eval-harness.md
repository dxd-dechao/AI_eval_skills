# SmartCampus Eval Harness

Version: Draft 1.0 — Jul 9, 2026
Supersedes: `eval-harness-langfuse-notes.md` (working notes, now folded in here)

This document specifies the **eval harness**: the custom runner that executes the
evals defined in the eval plan (doc 3) against the golden dataset (doc 4) and
writes evidence into Langfuse (doc 5). Docs 3–5 define *what* to measure and
*where* results live; this doc defines *what actually runs the measurement*, how
runs are triggered automatically, and where the automation boundary sits.

---

## 6A. Mental Model

```text
Langfuse      = experiment notebook / dashboard / evidence store
Eval harness  = machine that actually runs the experiment or audit
Actual app    = production system being evaluated
```

The production app and the harness both connect to Langfuse, but for different
reasons:

| Component | Responsibility | How it uses Langfuse |
|---|---|---|
| Actual app | Runs production/staging traffic | Logs traces, spans, metadata, costs, latency |
| Eval harness | Runs controlled evals, component diagnostics, and production audits | Loads dataset items, creates experiment runs, links traces, writes scores |
| Langfuse UI | Lets humans inspect and compare results | Shows traces, scores, dashboards, run comparisons |

**Key design principle — the harness must not duplicate app logic.**

Bad pattern:

```text
Harness has its own simplified video detection logic.
```

Good pattern:

```text
Harness calls the same app pipeline used in production:
app.pipeline.run_video_analysis(...)   # or the same service/container endpoint
```

The harness is separate from the app because it has different concerns
(controlled replay, baseline-vs-candidate comparison, judge execution, metric
computation, CIs, fairness slices, CI gates, reproducibility) — but it exercises
the same core code paths so the evaluation is realistic.

## 6B. Three Harness Modes

| Mode | Input | Ground truth? | Primary purpose | Typical output |
|---|---|---:|---|---|
| **1. Layer 2 golden eval** | Langfuse Dataset `golden-v1` (doc 4) | Yes | Release gates, regression testing, baseline comparison | Ground-truth metrics, CIs, pass/fail gates |
| **2. Layer 1 component eval** | Per-stage datasets/fixtures (see 6D) | Yes (per stage) | Diagnostics — which stage is the bottleneck; per-component release gates | Stage metrics vs stage targets (eval-plan 3C) |
| **3. Post-production judge audit** | Sampled production traces / completed cases | No | Quality monitoring, drift detection, triage, review queues | Judge-derived **proxy** scores, alerts |

Modes 1 and 2 are controlled evals against known labels. Mode 3 has no ground
truth: the LLM judge acts as a **proxy evaluator**, so its scores are monitoring
signals, never gate metrics (see naming rules in 6G).

## 6C. Mode 1 — Layer 2 Golden Eval (release gate)

```text
For each golden video in golden-v1:
  1. Load video URI, venue template, params, and expected annotations
  2. Run the real Layer 2 pipeline (same code path as production)
  3. Capture the resulting trace in Langfuse (environment=eval_run)
  4. Run the unified video judge in the harness (6G)
  5. Derive item-level metrics deterministically from the judge JSON:
     eval_recall, eval_precision, judge_classification, judge_temporal, ...
  6. Write scores back to the linked Langfuse trace / dataset run

After all videos:
  7. Aggregate by venue_type, tier (P0/P1/P2), positive/negative, fairness slice
  8. Compute confidence intervals (eval-plan 3H: Wilson / bootstrap)
  9. Check ship gates on lower CI bounds (eval-plan 3B, 3G)
  10. Write run-level summary scores to Langfuse
  11. Exit 0 (pass) or 1 (fail) — CI consumes the exit code
```

For the N=3 consistency requirement (eval-plan 3H), the harness executes three
named runs (see run naming in 6F) and computes the agreement rate across them.

## 6D. Mode 2 — Layer 1 Component Eval (diagnostics)

Layer 1 is not one mechanism. The seven stages of eval-plan 3C fall into **four
automation groups**, each with a different execution model:

| Group | Stages | Mechanism | Cost | Where the dataset lives |
|---|---|---|---|---|
| **A — Deterministic fixtures** | 2 (merge), 3 (combine) | Synthetic chunk-result JSON with deterministically known expected output; parameterized like unit tests | Seconds, free | In-repo: `eval_harness/fixtures/merge/`, `eval_harness/fixtures/combine/` |
| **B — Gemini component evals** | 1 (per-chunk analysis), 4 (summary triage) | Golden component datasets + real Gemini calls through the same code path the pipeline uses | Minutes, real token cost | Langfuse Datasets: `stage1-chunks-v1`, `stage4-triage-v1` |
| **C — Classic CV metrics** | 5 (D-FINE), 6 (InsightFace) | Annotated frames / identity pairs → sidecar endpoint (OIDC) or local container → COCO mAP, FAR/FRR — no LLM anywhere | Minutes, GPU cost | GCS media + in-repo manifest (`eval_harness/fixtures/dfine_manifest.json`, `face_manifest.json`) |
| **D — Retrieval eval** | 7 (semantic search) | Golden queries against a **pinned corpus** index built from a frozen Stage 1 output snapshot (eval-plan 3C Stage 7 compounding note) | Minutes, cheap | Langfuse Dataset `stage7-queries-v1`; pinned index `videoclips-eval-snapshot-v1` in S3 Vectors |

Notes per group:

- **Group A** runs on **every PR** — it is effectively pytest and needs no
  Langfuse round-trip (a CI check is the gate; optionally write run scores).
- **Group B, Stage 1** scores deterministically: system events are matched to
  chunk ground truth by behaviour type + temporal IoU ≥ 0.3 (the same matching
  rules as the unified judge's `verdict` rubric) — no judge call needed at the
  chunk level. Scores land as `chunk_recall` / `chunk_precision` (5D).
- **Group B, Stage 4** is the only text-in/text-out stage. Its deterministic
  triage metrics (P0 recall = 1.00, triage precision) come straight from labels;
  its faithfulness check is a *text* judge and is the one place a
  Langfuse-managed evaluator genuinely could run (see 6G).
- **Group D**'s pinned index is rebuilt only deliberately (a re-baselining
  decision, see 6I); day-to-day retrieval runs never touch the live index.

### Trigger routing — how Layer 1 runs automatically

The harness owns two routers plus a schedule:

**1. Change-based routing (CI, per PR).** A `stage_map.yaml` maps changed paths
to stages, so a PR runs only what it touches:

| Changed path | Stage triggered |
|---|---|
| `services/api/prompts/`, venue template service/models | Stage 1 |
| Merge/sanitization code, `gap_seconds` config | Stage 2 |
| Combine logic | Stage 3 |
| Summary prompt / `report_service` summary path | Stage 4 |
| `services/api/dfine_gpu/`, score thresholds | Stage 5 |
| `services/api/face_gpu/`, match thresholds | Stage 6 |
| Query rewrite prompt, `_build_caption`, embedding/index config | Stage 7 |
| *(always)* | Stages 2 + 3 (Group A is free) |

**2. Regression-based routing (from Layer 2).** The error-analysis decision tree
in eval-plan 3D is encoded as a routing table: when `gates.py` confirms a Layer 2
regression (drop beyond `trigger_threshold`, 3H), the harness automatically
enqueues the mapped diagnostic stage and writes results to Langfuse under a
linked run name, so error analysis starts with component data already in hand:

| Failing Layer 2 metric | Auto-enqueued Layer 1 run |
|---|---|
| Precision drop / hallucination signal | Stage 1 (FP on negatives, occupancy) |
| Recall drop | Stage 2 (boundary recall) + Stage 1 (per-chunk recall) |
| Classification accuracy drop | Stage 1 (per template version) |
| Temporal IoU drop | Stage 2 + Stage 1 (timestamp precision) |
| ROI count anomaly | Stage 5 |
| Face search quality drop | Stage 6 |
| Search quality drop | Stage 7 on pinned corpus (pass ⇒ escalate to Stage 1 caption quality) |

Example diagnostic run name: `stage1_diagnostic_for_layer2_2026-07-08`.

**3. Schedule.** Monthly regression (eval-plan 3E) includes Group A + any stage
whose upstream model had a version change since the last run.

## 6E. Mode 3 — Post-Production Judge Audit (proxy monitoring)

```text
For each sampled completed production case or trace:
  1. Load the video URI, app output, trace metadata, and system events
  2. Run the unified LLM judge using the production rubric (no ground truth)
  3. Derive judge-based quality signals:
     judge_pass_fail, judge_missing_event_suspected,
     judge_false_positive_suspected, judge_confidence
     (+ judge_classification / judge_temporal / judge_severity as proxy values)
  4. Write scores to the linked Langfuse production trace

After all cases:
  5. Aggregate quality trends by venue, template_version, model version, fairness slice
  6. Flag suspicious regressions / drift; build review queues
  7. Write batch-level summary scores to Langfuse
```

No golden dataset is required. Without ground truth the judge is a **proxy
evaluator**: useful for monitoring and triage, but `eval_recall`,
`eval_precision`, and any `ground_truth_*` names are **reserved** for Mode 1/2
runs where labels exist (see 6G).

### Sampling policy (cost control)

Judging with Gemini 2.5 Pro over production video is expensive; the audit runs
on a sample, never the full stream:

| Rule | Rate |
|---|---|
| Traces tagged `user_flagged` | **Always judged (100%)** — never sample away complaints (mirrors 5I #4) |
| Traces tagged `high_incident_count`, `failed_chunks`, `new_venue` | 100% |
| All other completed traces | Stratified random sample per venue_type — start at 10%/day |
| Floor | ≥ 20 judged traces per venue_type per week (raise sample rate if volume is low) |
| Budget cap | If daily judge cost exceeds budget, downsample the random stratum only — never the tagged strata |

The sample rate is a config value owned by DS; recalibrate after the first two
weeks of production data (same window as 5H DS #4).

### What a Mode 3 signal triggers

A judge-drift alert (5G) does not gate anything by itself — it triggers a
**targeted Mode 1 run** for the affected venue_type (eval-plan 3E). Proxy
signals route to ground-truth evals; they never replace them.

## 6F. Langfuse Configuration

### Environment separation

Use Langfuse's `environment` field (already in the 5C metadata schema) so eval
traffic never pollutes production dashboards:

```text
production | staging | eval_run
```

One Langfuse project with multiple environments is acceptable.

### Datasets

| Dataset | Mode | Contents |
|---|---|---|
| `golden-v1` | 1 | One item per golden video (schema below) |
| `stage1-chunks-v1` | 2 | 300+ annotated chunks (eval-plan 3C Stage 1 schema) |
| `stage4-triage-v1` | 2 | 50 event lists with ground-truth triage labels |
| `stage7-queries-v1` | 2 | 100+ graded-relevance queries + `corpus_snapshot_version` |
| *(none — in-repo fixtures)* | 2 | Stages 2/3 (synthetic JSON) and 5/6 (GCS media + manifests) |
| *(none — production traces)* | 3 | Mode 3 reads traces directly; only persist a sampled audit set as a Dataset if you deliberately want a reusable audit benchmark |

`golden-v1` item schema:

```text
input:
  - video GCS URI
  - venue_template_id
  - analysis params (mode: whole | chunked, chunk_duration, ...)

expected_output:
  - ground-truth event annotations (doc 4)

metadata:
  - venue_type
  - positive/negative case
  - priority tier (P0/P1/P2)
  - fairness stratification axes (doc 4 / eval-plan 3G)
```

Dataset names are **versioned** (`golden-v1`, `golden-v2`, …) because gates
compare candidate runs against baselines on the **same dataset version**.

### Experiment runs and naming

Controlled evals (Modes 1 and 2 Groups B/D) run as Langfuse **Dataset Runs**:
the harness iterates dataset items via the SDK and runs the real pipeline inside
the dataset-item context, so each resulting trace links to both the dataset item
and the named run.

```text
layer2_2026-07-08_templateV3_gemini3flash_run1of3
layer2_2026-07-08_templateV3_gemini3flash_run2of3
layer2_2026-07-08_templateV3_gemini3flash_run3of3

stage1_2026-07-08_templateV3
stage1_diagnostic_for_layer2_2026-07-08
postprod_audit_2026-07-08          # Mode 3 batch label (scores on production traces)
```

This enables baseline-vs-candidate and noise-band comparison directly in
Langfuse's run-comparison view.

## 6G. Judge Execution

**The unified video judge runs in the harness, not inside Langfuse** — in every
mode. Langfuse-managed LLM-as-judge evaluators operate on trace text; the
Layer 2 judge must inspect video clips, system events, and (in Modes 1/2)
ground-truth annotations. So the harness calls the judge (Gemini 2.5 Pro, strict
JSON schema per eval-plan 3B), validates the structural constraints, and derives
all metrics deterministically from the JSON. Langfuse stores the resulting
scores; it never executes the judge.

**Exception:** Stage 4 summary faithfulness is text-only (event list vs summary)
and may run as a Langfuse-managed evaluator if convenient; keeping it in the
harness is also fine for consistency.

### Canonical score names

One judge call, one naming registry (the registry of record is 5D):

| Context | Score names |
|---|---|
| Ground truth available (Modes 1/2) | `eval_recall`, `eval_precision`, `eval_classification_accuracy`, `eval_temporal_iou`, `eval_fp_rate`, `judge_detection`, `judge_classification`, `judge_temporal`, `judge_faithfulness`, `judge_severity`, `chunk_recall`, `chunk_precision`, `merge_completeness`, `fairness_disparity_*`, `adversarial_pass` |
| No ground truth (Mode 3) | `judge_pass_fail`, `judge_missing_event_suspected`, `judge_false_positive_suspected`, `judge_confidence` (+ proxy reuse of `judge_classification` / `judge_temporal` / `judge_severity`) |

Rules:

- All `judge_*` scores derive from **one unified judge call** per item
  (eval-plan 3B) — the five legacy names survive for dashboard continuity, but
  there are not five judges.
- The canonical temporal score name is **`judge_temporal`** (not `judge_timing`).
- `eval_*` / `ground_truth_*` names are **reserved for runs with labels**.
  Mode 3 must never emit them.
- The judge's one-sentence rationale is attached as the Langfuse score
  **comment**, not a separate score.

## 6H. Aggregates, Gates, and CI

Per-trace scores are point values (5D). The harness computes run-level and
slice-level aggregates — venue-level recall/precision, P0-only recall,
negative-case FP rate, fairness disparity ratios, Wilson/bootstrap CIs — and
enforces the ship gates from eval-plan 3B/3G/3H:

```text
gate passes ⇔ lower 95% CI bound ≥ target threshold (per venue, per tier)
```

Division of labor:

```text
Harness  = computes metrics and enforces gates (exit 0 = pass, exit 1 = fail)
Langfuse = stores and visualizes the gate evidence (Dashboard 3)
CI       = blocks merge/release when the harness exits non-zero
```

Langfuse is never responsible for enforcing a gate. Mode 3 aggregates are
monitoring/triage signals, not gates (6E).

## 6I. Automation Boundary

What the harness automates, what it automates only after a human pulls the
trigger, and what can never be automated. This boundary is load-bearing: the
harness removes *execution* toil, not *judgment* or *labeling*.

### Fully automated (no human in the loop)

- Group A fixture evals on every PR (Stages 2/3)
- Change-based stage routing in CI (`stage_map.yaml`)
- Mode 1 golden runs end-to-end: pipeline replay, judge calls, metric
  derivation, CI computation, gate check, exit code
- Regression-based routing: confirmed Layer 2 drop → auto-enqueued Layer 1
  diagnostic run (6D)
- Mode 3 sampled audits, proxy score writing, drift alerts (5G)
- Score writes, run comparison, dashboard population in Langfuse

### Automated execution, human-triggered decision

- **Re-baselining** — the 5-run noise-band re-establishment after a Gemini model
  update (3H) runs mechanically, but *deciding* to accept a new baseline is human
- **Pinned corpus rebuild** (Stage 7) — rebuilding `videoclips-eval-snapshot-v*`
  re-baselines caption quality; a deliberate, versioned decision
- **Dataset version promotion** (`golden-v1` → `golden-v2`) — the upload is
  scripted; deciding the composition is human
- **Judge or judge-model changes** — swapping the judge model re-runs
  calibration automatically, but the change itself is a reviewed decision

### Never automatable (human-only, permanently)

- **Ground-truth creation** — annotating golden videos, the 300+ Stage 1 chunks,
  D-FINE frame boxes, InsightFace identity pairs, Stage 4 triage labels, graded
  query relevance, and the access-controlled fairness axis labels (3G privacy
  note). The harness automates execution and routing, never labeling.
- **Judge calibration** — the 80–100 human-scored items and per-field agreement
  gates (eval-plan 3B) are what make judge scores trustworthy at all; humans
  are the reference, and recalibration is required on any judge change.
- **Adversarial case crafting** — the 90–110 adversarial items (3G) are
  explicitly "expensive to craft — quality over quantity"; red-team creativity
  does not automate.
- **Human verification in the app** — `verification_status` flags (and the
  `human_flag_reason` taxonomy, 5D) are the only production signal with human
  judgment behind it; Mode 3 proxy scores complement but never replace it.
- **Root-cause diagnosis** — the harness delivers the component data
  pre-gathered (6D routing), but reading it, naming the root cause, and choosing
  the fix is engineering/DS judgment.
- **Ship/no-ship sign-off** — gates are enforced mechanically, but the pre-ship
  release review (Layer 2 full + adversarial + fairness, eval-plan 3E) is a
  human decision informed by the gate evidence, not replaced by it.
- **Dataset maintenance judgment** — the harness *can* automatically surface
  candidates for new golden items (flagged traces, judge-suspected misses); a
  human decides what enters the dataset and labels it.

## 6J. Repository Layout and Interaction Modes

### Suggested layout

```text
eval_harness/
  run_layer2.py              # Mode 1 CLI entrypoint
  run_layer1.py              # Mode 2 CLI entrypoint (--stage 1..7)
  run_postprod_judge.py      # Mode 3 CLI entrypoint
  stage_map.yaml             # change-based + regression-based routing tables (6D)
  dataset_loader.py          # loads Langfuse dataset items (Modes 1/2)
  trace_loader.py            # loads sampled production traces (Mode 3)
  pipeline_adapter.py        # calls the real app pipeline / per-stage code paths
  judge_runner.py            # calls the Gemini video judge (6G)
  metrics.py                 # recall, precision, IoU, mAP, FAR/FRR, nDCG, CIs
  langfuse_writer.py         # creates runs, links traces, writes scores
  gates.py                   # pass/fail logic + regression router hook
  fixtures/
    merge/                   # Stage 2 synthetic chunk-result sequences
    combine/                 # Stage 3 synthetic multi-duration sets
    dfine_manifest.json      # Stage 5 GCS frame manifest
    face_manifest.json       # Stage 6 GCS frame + identity-pair manifest
```

### 1. CLI

```bash
python -m eval_harness.run_layer2 \
  --dataset golden-v1 \
  --run-name layer2_2026-07-08_templateV3_gemini3flash_run1of3 \
  --candidate-config configs/template_v3.yaml

python -m eval_harness.run_layer1 --stage 1 --dataset stage1-chunks-v1 \
  --run-name stage1_2026-07-08_templateV3

python -m eval_harness.run_postprod_judge \
  --environment production \
  --since 2026-07-08T00:00:00+08:00 \
  --until 2026-07-08T23:59:59+08:00 \
  --judge-config configs/unified_judge.yaml
```

### 2. CI/CD gate

```text
On PR:
  always run Group A (Stages 2/3 fixtures)
  run stages routed by stage_map.yaml for the changed paths
  fail CI on exit 1

On release candidate:
  run full Mode 1 (N=3) + adversarial suite + fairness track
  compare candidate vs baseline (3H two-variant rule)
  fail CI if any lower CI bound is below threshold
```

### 3. Notebook / analyst workflow

```python
run_layer2_eval(
    dataset="golden-v1",
    limit=10,
    venue_type="canteen",
    positive_only=True,
)
```

Useful for inspecting failures, replaying specific videos, running small slices
before a full eval, and comparing judge output to ground truth.

### 4. Scheduled batch jobs

```text
Nightly:  Mode 3 post-production audit over yesterday's sampled traces (6E)
Monthly:  Mode 1 full regression (N=3) + Group A + stale-stage refresh (3E)
```

## 6K. Key Takeaways

- The harness is separate from the app but calls the **same production code
  paths** — never a reimplementation.
- Three modes: golden Layer 2 (gates), Layer 1 component (diagnostics,
  auto-routed), post-production judge (proxy monitoring, sampled).
- Layer 1 automation is per-group: fixtures run free on every PR; Gemini/GPU/
  retrieval stages run when routed by code changes or Layer 2 regressions.
- The unified video judge runs **in the harness**; Langfuse stores its scores
  but cannot execute it. `eval_*` names require ground truth; Mode 3 emits
  proxy `judge_*` names only.
- Harness computes and enforces gates; CI blocks on exit code; Langfuse is the
  evidence record and comparison UI.
- Automation covers execution, routing, and alerting. Labeling, judge
  calibration, adversarial crafting, root-cause diagnosis, and ship sign-off
  are permanently human.
