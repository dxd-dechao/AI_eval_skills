## 5A. Core Langfuse Concepts Mapped to SmartCampus

| Concept | Definition | What it maps to in SmartCampus |
|---------|-----------|--------------------------------|
| **Trace** | One complete job from start to finish, with a single `trace_id`. | One **video analysis run** — from the moment `POST /api/v1/analyze` is called to the final merged/combined result being written. The `analysis_id` (UUID) serves as the trace_id. |
| **Span** | One step within a trace; has start/end time, inputs, outputs; nests hierarchically. | Each pipeline stage: chunking, per-chunk Gemini call, merge, combine, summary generation, semantic indexing, face indexing. |
| **Generation** | A special span for an LLM call — adds model name, prompt template, completion, token counts, cost. | Each Gemini 3 Flash call: per-chunk video analysis, summary generation, query rewrite, case synthesis. Also the embedding generation (gemini-embedding-2). |
| **Score** | A quality judgment attached to a trace/span/generation. Decision scores are per approved criterion and carry the evaluator version and acceptance state. | Event `verification_status` (correct/wrong/unreviewed) from the app, deterministic Layer 1 diagnostics, and candidate criterion scores. Production monitors use a `proxy_` prefix and are not baselines. |
| **Session** | A group of related traces. | All analyses for the same **video_id** in the same day. This lets you see how re-runs or multi-duration analyses on the same video compare. Alternatively: all analyses triggered by a single batch upload. |

### The trace_id is the glue

The `analysis_id` (UUID, generated in `start_analysis()`) must:
1. Be sent to Langfuse when creating the trace (backend instrumentation)
2. Be stored in Firestore alongside the analysis record (already done — `analysis_data["analysis_id"]`)
3. Be passed to the frontend via the analysis response (already available in the API response)
4. Be used by the eval pipeline to write scores back to the correct trace
5. Be included in event records so human verification flows back to the trace

This is already the case architecturally — `analysis_id` is the natural trace_id.

## 5B. Trace Structure

### Format 1: Compact tree

```
Trace: analysis_{analysis_id} (one per video analysis run)
├── Span: "pipeline_init" (chunk calculation, task dispatch)
│
├── Span: "batch_0" (chunks 0–9)
│   ├── Span: "chunk_0" → Generation: "gemini_video_analysis" (tokens, cost)
│   ├── Span: "chunk_1" → Generation: "gemini_video_analysis"
│   ├── ...
│   └── Span: "chunk_9" → Generation: "gemini_video_analysis"
│
├── Span: "batch_1" (chunks 10–19)
│   └── ... (same structure as batch_0)
│
├── Span: "merge" (deterministic post-processing)
│   ├── Span: "timestamp_offset"
│   ├── Span: "sanitization"
│   └── Span: "consecutive_merge"
│
├── Span: "combine" (multi-duration only)
│
├── Span: "summary_generation" → Generation: "gemini_summary" (tokens, cost)
│
├── Span: "semantic_indexing" → Generation: "gemini_embedding" (tokens)
│   └── (per-chunk embedding calls)
│
└── Span: "face_indexing" (parallel, fire-and-forget)
    └── (per-chunk face_gpu calls)
```

### Format 2: Detailed breakdown

#### Span: pipeline_init
- **Inputs:** video_id, venue_template_id, analysis_mode, chunk_duration_seconds
- **Outputs:** {num_chunks, num_batches, pipeline_mode, chunk_durations}
- **Metadata:** {video_duration_s, resolution, template_version}

#### Span: batch_N → Span: chunk_N → Generation: gemini_video_analysis
- **Inputs:** video GCS URI, chunk time window [start_s, end_s], user_prompt
- **Outputs:** Parsed schema result (incident list, flags, scene_description)
- **Generation metadata:**
  - Model: `gemini-3-flash-preview`
  - Prompt template: `{venue_template_id}@v{version}`
  - Token counts: {prompt_tokens, candidates_tokens, total_tokens}
  - Thinking tokens: {thinking_budget_tokens}
  - Latency: ms
  - Temperature: 0.1, Seed: configured, Media resolution: configured

#### Span: merge
- **Inputs:** {chunk_results_count, failed_chunks_count}
- **Outputs:** {incidents_before_merge, incidents_after_merge, incidents_discarded, merge_ratio}
- **Metadata:** {gap_seconds: 5.0, boundary_events_count}

#### Span: combine (multi-duration only)
- **Inputs:** {durations: [30, 60, 120], per_duration_event_counts}
- **Outputs:** {combined_event_count, overlap_merges, preserved_unique}
- **Metadata:** {combine_method: "interval_merge_by_type"}

#### Span: summary_generation → Generation: gemini_summary
- **Inputs:** event list (max 80 events, descriptions truncated to 160 chars)
- **Outputs:** AnalysisSummary {headline, groups: [{priority, event_ids}], notes}
- **Generation metadata:**
  - Model: `gemini-3-flash-preview`
  - Token counts, latency
  - Cache hit: boolean (hash of events matches previous run)

#### Span: semantic_indexing → Generation: gemini_embedding
- **Inputs:** {chunks_to_index, captions}
- **Outputs:** {attempted, indexed, skipped, failed}
- **Generation metadata:**
  - Model: `gemini-embedding-2`
  - Dimensions: 1536
  - Per-chunk: token count

#### Span: face_indexing
- **Inputs:** {chunk_windows, video_id}
- **Outputs:** {faces_detected, faces_indexed, faces_matched, unknown_count}
- **Metadata:** {model: "buffalo_l", embedding_dim: 512, confident_matches, candidate_matches}

## 5D. Score Design

Decision scores are one binary result per approved criterion. The name binds the criterion id and version to the evaluator id and version. Each row records acceptance state. Unaccepted rows stay diagnostic. This sample is a SmartCampus candidate registry: no row below is an accepted operational evaluator, and none of the names is a 1–5 scale.

| Score name | Type | Route | Attached to | Acceptance | Purpose |
|------------|------|-------|-------------|------------|---------|
| human_flag | numeric (0/1) | App user (event verification) | Trace | Production signal. Not a rubric approval. | Did any user mark an event as wrong? (1 = at least one event flagged wrong) |
| human_flag_reason | categorical | App user | Trace | Production signal. | Error classification — see taxonomy below |
| criterion.C-detect.v1.det-events.v1 | categorical (Pass/Fail/Unscorable) | deterministic | Trace | candidate — not accepted | Binary: every labelled P0/P1 event in the development item is matched, or it is not. Illustrative criterion. |
| criterion.C-temporal.v1.det-iou.v1 | categorical (Pass/Fail/Unscorable) | deterministic | Trace | candidate — not accepted | Binary overlap check against the Product-approved overlap rule. The numeric IoU may be stored as evidence on the score comment. It is not the decision score. |
| criterion.C-type.v1.human-type.v1 | categorical (Pass/Fail/Unscorable) | named human | Trace | candidate — pending named review | Named expert verdict on behaviour type for one item. |
| criterion.C-faithful.v1.llm-faithful.v1 | categorical (Pass/Fail/Unscorable) | optional LLM | Generation | candidate — unaccepted, shadow only | Semantic faithfulness of the description. Shadow until a held-out acceptance record exists for this evaluator version. |
| layer1.chunk_recall | numeric (0–1) | deterministic component | Span (chunk) | diagnostic | Per-chunk detection recall. Layer 1. Not a ship gate by itself. |
| layer1.chunk_precision | numeric (0–1) | deterministic component | Span (chunk) | diagnostic | Per-chunk detection precision. |
| layer1.merge_completeness | numeric (0–1) | deterministic component | Span (merge) | diagnostic | Events preserved through merge. |
| layer1.fairness_disparity_skin_tone | numeric | fairness diagnostic | Trace | diagnostic — no numeric gate in this sample | Observed disparity ratio for skin_tone. A gate needs a Product-approved minimum; this sample does not set one. |
| layer1.fairness_disparity_age_band | numeric | fairness diagnostic | Trace | diagnostic | Observed disparity ratio for age_band. |
| layer1.fairness_disparity_gender | numeric | fairness diagnostic | Trace | diagnostic | Observed disparity ratio for gender_presentation. |
| layer1.fairness_disparity_lighting | numeric | fairness diagnostic | Trace | diagnostic | Observed disparity ratio for lighting. |
| layer1.fairness_disparity_camera_angle | numeric | fairness diagnostic | Trace | diagnostic | Observed disparity ratio for camera_angle. |
| layer1.fairness_disparity_attire | numeric | fairness diagnostic | Trace | diagnostic | Observed disparity ratio for attire. |
| criterion.C-adversarial.v1.det-adversarial.v1 | categorical (Pass/Fail/Unscorable) | deterministic | Trace | candidate — not accepted | Binary: adversarial item behaved as the approved fail rule requires. |

Provenance on every decision score: criterion id/version, evaluator id/version, acceptance state, and a link to `evaluator-register.json`. A comment may hold the rationale or the supporting IoU. The comment is not a second score and not a 1–5 grade.

### Production monitoring proxies

Written on sampled production traces (harness doc 6E). Every name uses the `proxy_` prefix. These rows are monitoring signals. They are omitted from decision metrics and from baselines.

| Score name | Type | Source | Attached to | Purpose |
|------------|------|--------|-------------|---------|
| proxy_suspected_miss | numeric (0/1) | Production monitor | Trace | Monitor suspects a real event was missed. Not a recall baseline. |
| proxy_suspected_false_positive | numeric (0/1) | Production monitor | Trace | Monitor suspects a reported event is not real. Not a precision baseline. |
| proxy_monitor_note | categorical | Production monitor | Trace | Short note stored as the score comment. Not a decision verdict. |

### `human_flag_reason` taxonomy

| Value | Meaning | Maps to failure mode |
|-------|---------|---------------------|
| `not_an_incident` | Reported event is not actually a concerning behaviour | False positive (precision) |
| `wrong_type` | Event happened but was categorised incorrectly | Classification error |
| `wrong_time` | Event is real but timestamps are significantly off | Temporal precision |
| `wrong_person` | Event attributed to wrong individual / location | Description faithfulness |
| `duplicate` | Same event reported multiple times | Merge failure |
| `missed_event` | User knows of a real event that wasn't detected | False negative (recall) — user-initiated |
| `severity_wrong` | Event real and correctly typed but confidence level wrong | Severity miscalibration |

**Frontend integration:** The event verification UI (existing `verification_status` field) already supports correct/wrong. The `human_flag_reason` taxonomy is the requirement for extending that UI to capture WHY an event was marked wrong. Currently not implemented — spec as the frontend requirement.

**Per-trace scores are point values.** No CIs attached to individual trace scores. CIs apply at the aggregate level (eval-plan 3H).

## 5E. How Scores Flow In

```
Source 1: App users → mark event correct/wrong → human_flag + human_flag_reason on trace
  (Frontend verification_status → backend event update → Langfuse score write)

Source 2: Eval pipeline → development or held-out items → one binary score per
  routed criterion (criterion.C-*.v*.evaluator.v*) on traces
  (Batch process: for each item, run system, apply that criterion's route, write the score
  with criterion version, evaluator version, and acceptance state)

Source 3: Automated tags → high_incident_count, failed_chunks → tags on traces
  (Backend post-pipeline hook, no ground truth needed. Tags are not decision scores.)

Source 4: Optional LLM route → criterion.C-faithful.v1.llm-faithful.v1 on a generation
  only when that route exists in the register. Unaccepted runs stay shadow.
  (No unified judge. No 1–5 score. Prompt text comes from the approved criterion.)

Source 5: Fairness diagnostic → layer1.fairness_disparity_[axis] on eval-run traces
  (Aggregate observation. Not a gate unless Product has approved a minimum.)

Source 6: Adversarial criterion → criterion.C-adversarial.v1.det-adversarial.v1
  on adversarial-set traces (binary pass/fail/unscorable for that candidate criterion)

Source 7: Production monitor → proxy_suspected_miss, proxy_suspected_false_positive,
  proxy_monitor_note on sampled production traces
  (Scheduled sample WITHOUT ground truth. proxy_ names only. Never copied into a baseline.
  Sampling policy is in harness doc 6E.)
```

## 5G. Alerts

| Alert type | Condition | Action |
|------------|-----------|--------|
| System down | Analysis volume < 20% of 7-day average for 6 hours | Investigate Cloud Run / Cloud Tasks health |
| Chunk failure spike | Chunk error rate > 5% in 1-hour window | Check Gemini API status, quota, model errors |
| Latency spike | p95 trace duration > 10 minutes | Check batch parallelism, Gemini latency, network |
| Quality drop (human signal) | Human flag rate > 2× 30-day average for any venue | Trigger targeted eval for that venue_type |
| Hallucination signal | Empty-room FP rate spikes (incidents on known-empty videos) | Investigate prompt/model regression |
| Cost anomaly | Daily token cost > 3× 7-day average | Check for retry loops, extremely long videos, batch reprocessing |
| Distribution shift | Confidence distribution shifts > 2σ from baseline | Run component eval |
| Schema parse failure | > 2% parse failure rate in 1 hour | Check Gemini structured output format changes |
| Proxy monitor drift | 7-day mean of proxy_suspected_miss moves sharply for any venue | Trigger a targeted Layer 2 diagnostic for that venue_type (harness doc 6E). The proxy series is not a baseline and does not gate. |

## 5H. Integration Points

### Engineers must:

1. **Install Langfuse Python SDK** (`langfuse`) in `services/api/requirements.txt` / `pyproject.toml`
2. **Wrap the analysis pipeline** — create trace at `start_analysis()`, create spans at each stage boundary (init, chunk processing, merge, combine, summary, indexing)
3. **Instrument Gemini calls** — wrap `self._genai_client.models.generate_content` in generation spans (capture prompt, output, token counts, model, config)
4. **Attach metadata** — trace-level metadata from analysis record fields; span-level metadata from processing results
5. **Store trace_id** — already done: `analysis_id` in Firestore. Ensure it's in API responses to frontend.
6. **Pass trace_id to frontend** — already available via analysis API response (the `analysis_id` field)
7. **Write human scores** — when `verification_status` is updated on an event, write the corresponding Langfuse score using the `analysis_id` as trace_id

### DS must:

1. **Configure dashboards** — build the 4 dashboards in Langfuse UI using the metadata/score schema above
2. **Set up alerts** — configure threshold-based alerts per 5G table
3. **Build eval pipeline** — golden dataset → run system → compute metrics → write scores back to Langfuse traces via SDK
4. **Define proxy metric thresholds** — calibrate alert thresholds based on initial production data (first 2 weeks after instrumentation)
5. **Write criterion scores from the harness** — each approved criterion has its own route. Deterministic and human scores are written by the harness. An optional LLM route, if the register has one, also runs in the harness because a video criterion needs the clip, not trace text alone. Langfuse stores the score, the version, and the acceptance state. It does not invent a judge.
6. **Prompt management (optional)** — register venue template versions in Langfuse prompt registry for auto-versioning and comparison

## 5I. Common Misconceptions to Preempt

1. **Langfuse is a sink** — data flows IN from your backend via the SDK. It does not pull from Firestore, GCS, or Cloud Tasks. You must actively instrument each span.

2. **Trace ID is the glue** — the `analysis_id` must be stored in Firestore (done), passed to the frontend (done via API), AND used to write Langfuse traces. Without this, you cannot link human flags to model traces.

3. **Not real-time alerting** — Langfuse records data for analysis. Use it to detect trends and trigger investigations. For real-time system health, keep Cloud Monitoring alerts alongside Langfuse.

4. **Sampling** — Start at 100% trace capture. Once baselines are established (Phase 3), consider sampling to 50% for high-volume venues. **Never sample away user complaints** — traces with `human_flag = 1` are always captured.

5. **Prompt management** — Optional but powerful. Register each venue template version in Langfuse's prompt registry. Then any generation span automatically links to its template version, enabling before/after comparisons without custom metadata.

6. **Datasets feature** — Langfuse has built-in dataset management for offline eval. The golden dataset and the Layer 1 component datasets live here as versioned Datasets, and eval runs are Dataset Runs — but the **harness** executes the eval, not Langfuse. See harness doc 6F for the dataset/run configuration.

7. **Cost tracking** — Automatic if generations are instrumented with model name + token counts. Langfuse computes cost using its built-in pricing table. Gemini pricing may need manual configuration if not in the default table.

8. **Langfuse stores evidence; the harness enforces gates** — decision scores are computed in the harness from accepted routes. CI blocks on the harness exit code. A preflight refusal is a blocked run, not a Product-quality failure. Production monitors run on a **sample** of traces (always including `user_flagged` ones) and write only `proxy_` scores. The sampling policy is in harness doc 6E.
